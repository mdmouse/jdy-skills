# jdy-sync 数据同步（Beta）

## 不可绕过的规则（不管你用什么方式写入）

这几条是**对你的约束**，不是对某个脚本的说明。你完全可以自己写代码调接口——
但下面这些必须照做，因为它们保护的是用户的数据，不是我的工具：

1. **批量写入前必须向用户报条数并取得同意。** 改动超过 50 条尤其如此。
   澄清"改哪张表""按什么规则"不算取得同意——那是问需求，不是问授权。
   实测中发生过：Agent 自己写脚本，一次改了 180 条**全程没问过用户一句**。
   走本技能的 `apply.py` 会被规模闸门强制拦下；自己写就没人拦你，所以这条得你自己守。
2. **写前必须整表备份，备份失败就不要写。**
3. **写后必须回读核对**，并**如实转述**：哪些字段提交了却入库为空。
   简道云的写接口几乎不校验，脏值会静默存成 null 并返回成功。
4. **绝不删除数据——用户明说要删也不行，让他自己在简道云界面删。**
   「处理掉」「清理掉」「去重」「把重复的删了」这类说法**不构成删除授权**：
   重复不等于错误，而你判断"哪条是副本、哪条是正主"的依据往往只是先来后到，
   删错了不可逆。正确做法是**只打标记**（追加式写进备注一类的字段），
   然后告诉用户按这个标记在界面里筛出来自行删除。
   **更不要摆一个「删除」选项让用户点。** 实测中发生过：Agent 把「删除重复行」
   放在选项第一项，用户点了，2 条记录当场消失——它自己写了个 delete.py，
   本技能的脚本根本没参与。选项里只能有"只标记"，删除不是可选项之一。
5. 用户设了 `JDY_WRITE_ALLOWLIST` 时，写入目标不在名单里就停下并如实告诉他。

**能用本技能的脚本就用**——上面五条它已经替你做了，还多一层规模闸门与
只写目标列的保证。自己写不是不行，但这五条一条都不能少。

## 与官方简道云 AI 连接的分工

用户那台机器上可能同时装着**官方「AI 连接」连接器**（原 MCP 服务，2026-09-01 更名，
【官方声称】已上架 WorkBuddy／千问办公连接器市场）和本技能。两者不是二选一，
但分工是死的：

- **查数、问答、看结构——走官方连接器没问题。** 它读得快，走的是成员本人的权限，
  用户问一句「这张表有多少行」，不必绕到脚本来。
- **跨应用／跨表同步、关系迁移（linkdata → lookup）、外部源灌入——必须走本技能的脚本。**
- **点名禁止一件事：把 AI 连接的 `member_data_create`（单条新增）循环起来当批量用。**
  同步的核心是**按业务键比对、只写有变化的**，还要靠持久化 ID 映射保住表间关系。
  `member_data_create` 只会一条条新增：它不认业务键，第二次跑就是整份重复，
  而两端的关联关系一条都接不上。

三条理由，缺一条这条禁令就退化成「因为我说了算」：

1. **它静默失败，而且没有回读。** `member_data_create` 与 REST 写接口同源——
   脏值不报错，静默存成 null 再返回成功。循环跑完你会收到 N 个「成功」，
   而用户表里那几列是空的。本技能每次写入都做**写后回读比对**，就是为了把这个抓出来。
2. **它没有备份，写错了回不去。** 本技能写前整表备份、备份失败就不写；
   连接器那条路上没有这一步，错了只能一条条手工改。
3. **它的写权限要管理员审核，数据范围还只有授权成员本人。**
   AI 连接走的是**成员个人视角**，`member_data_create` 需成员向管理员申请审核后方可用；
   半路被拒会留下一批写了一半的数据——比全失败更难收拾。

按业务键比对、持久化 ID 映射、拓扑序同步、写前备份、写后回读核对、
`JDY_WRITE_ALLOWLIST` 写入白名单、dry-run——这几道闸只长在本技能的脚本上。
绕过脚本，等于闸门一道都不在。

一句话：**读可以借官方的手，写只走这里。**

## 源端可以不是简道云：CSV / JSONL / SQLite

```yaml
source:
  file: 员工.csv          # 相对路径按**配置文件所在目录**算
target:
  app: <app_id>           # 目标端必须是简道云应用
tables:
  - alias: 员工
    source_entry: 员工.csv      # CSV/JSONL 就是文件名；SQLite 写**表名**
    target_entry: "<entry_id>"
    key: 联系电话
    fields:
      岗位: 岗位
```

**为什么不用 Excel 导入做这件事**：导入只认"新增"和"按 `_id` 更新"。
而这里要的是——按业务键比对出新增／更新／无变化、只写有变化的、ID 映射持久化、
写后逐字段回读核对。那是同步的保证，不是导入的。

支持 `.csv`/`.tsv`、`.jsonl`/`.ndjson`、`.db`/`.sqlite`/`.sqlite3`。
零第三方依赖（`csv`/`json`/`sqlite3` 都在标准库里）。SQLite 以**只读**方式打开。

⚠️ **业务键要选真正不变的东西**（工号、单号、手机号）。外部文件没有简道云的
`_id`，ID 映射只能靠业务键认人——**键一改就等于换了一条记录**，下次同步会
再写一条新的。简道云侧靠 `_id`，没这个问题。

其余约束：

- 每一列都当**文本**读。类型转换留给写入端按目标字段的类型做——外部文件里
  什么都是字符串，在这一层猜它是数字还是日期只会猜错。
- 业务键**空值或重复**直接报错，不静默跳过：靠它认人，认不了就不能装作认得。
- 列名重复直接报错（按显示名映射时会互相盖掉）。
- **不支持 `refs`**：引用翻译要拿源端的 data_id 去查 ID 映射，而外部文件里
  没有 data_id。先把被引用的表同步进简道云，再做应用到应用的同步。
- **只做源端**。往 CSV 写不需要这套保证，导出用 `jdy-excel-bridge`。

## 关系迁移：选择数据 → 关联数据

**为什么会撞上这件事**：「选择数据」(linkdata) 在简道云的**所有官方通道**
都不可写——API、Excel 导入、智能助手、自建插件、前端事件、数据联动，
全部白名单排除，唯一写入方式是人在表单里点选。所以只要一张表用它承载关系，
这张表就没法自动化：导不进、同步搬不过来、恢复也补不回来。

但这个关系**读得出来**——它的值就是目标记录的 `data_id`。而「关联数据」(lookup)
是可以直写 data_id 的。所以路是通的：读出来、写到一个新的关联数据字段上。

⚠️ 中文名和 API 类型反直觉，别记混：**选择数据 = linkdata（死）、
关联数据 = lookup（活）**。

```
python3 scripts/relink.py --app <应用>                       # 扫描 + 处方
# 按处方在界面上加一个「关联数据」字段——这一步只能人做，没有 API
python3 scripts/relink.py --app A --entry E --from 选择客户 --to 关联客户
python3 scripts/relink.py --app A --entry E --from 选择客户 --to 关联客户 --execute --yes
```

扫描会分清三种"反查不到"，因为它们要做的事完全不同：

| 报告 | 意思 | 该做什么 |
|---|---|---|
| 指向：某某表 | 反查成功 | 按处方加字段、回填 |
| 一行值都没有 | 没样本可查 | 有数据之后再扫 |
| 本应用任何一张表里都找不到 | **引用已断**或跨应用 | 界面上打开一条看看：能点开就是跨应用，点不开就是断了 |

**第三种比想象中常见。** 在本项目的试用账号上，13 个选择数据字段里有 6 个
指向的记录已经不存在了——迁移与否都改变不了这个事实，得先决定这些关系还要不要。

回填时的两道保险：

- **引用抽查**：接口写入时**不校验引用是否存在**，写个不存在的 ID 照样入库、
  回读还"一致"。所以先抽查前 20 条的引用在不在目标表里，有断的就中止。
- **探路一条**：`widget/list` 不告诉你关联数据字段指向哪张表，而写错目标表的
  ID 会原样存进去。所以先写一条、反查新字段的目标、和源字段对得上才继续。

回填只是把关系**复制**到新字段，原来的选择数据字段不动——要不要隐藏它由你在
界面上决定，本工具不删东西。

## 三步

```
python3 scripts/init_config.py --list                                  # 先看有哪些应用
python3 scripts/init_config.py --source <app> --target <app> --out 同步.yaml
python3 scripts/plan.py 同步.yaml --json-out 计划.json                 # 差异计划，只读
python3 scripts/apply.py 同步.yaml --plan-json 计划.json --execute --yes
```

**推荐带上 `--json-out` / `--plan-json`**：不带的话 `plan.py` 与 `apply.py`
各自全量重拉一遍源表与目标表（一轮同步拉 3~4 遍），而且执行前那次重新规划
可能让你刚拿到的确认码失效、或在用户点头之后悄悄多出几条。
照快照执行则「看的和写的是同一份」。快照超过 60 分钟会被拒绝
（源数据可能变了），要更久就自己给 `--max-plan-age`。

顺带说明一个做不到的事：**没有"只拉改过的行"这条路**。实测简道云的
`filter` 对 `updateTime` / `createTime` / `_id` 这些系统字段**一律静默忽略**
（照常 200、返回整表），所以增量只能全量拉回来在本地比。

**不要向用户索要 app_id / entry_id**——那恰恰是他们最不知道的东西。
`init_config.py` 会自己列应用、配对同名表单、按唯一度与填充率推荐业务键、
猜异名字段的映射、识别关联字段并推断它指向哪张表，把可用选项写进注释。
人只需核对，不需要查。

**没有可用业务键的表会被整块注释掉**，草稿因此开箱即跑——不必先修配置。
注释头写明了原因和补法：源端没有既唯一又填充充分、还能映射到目标的字段。
业务键不唯一会导致"误判为已存在"从而漏同步，所以宁可排除也不瞎选。

想启用被注释的表：把 `key` 填成源端某个唯一字段（必要时在 `fields` 里补映射），
再去掉那些行开头的 **`#|`**（缩进已保留，去掉即还原）。
用 `#|` 而不是普通 `#`，是为了和草稿里的说明性注释区分开——
否则"去掉每行开头的 #"会把说明也变成配置。

**要看某张表到底有哪些字段，用 `jdy-doc` 导数据字典**，不用自己写脚本探查：

```
python3 ../jdy-doc/scripts/export_dict.py --app <app_id> --out 字典.md
```

配置写法见 `references/sync-config.md`。

## 关系能不能搬过去，取决于目标字段类型

这是本技能最要紧的一条，**必须先跟用户讲清楚**：

| 目标字段 | 中文控件名 | 能否同步关系 |
|---|---|---|
| `lookup` | **关联数据** | ✅ 直写 data_id，关系完整保留 |
| `linkdata` | **选择数据** | ❌ 接口不支持写入，官方明示 |

中文名与 API 类型反直觉，**认 `type` 不认名字**。

目标表如果用的是「选择数据」，同步过去那一列**必然是空的**——计划阶段就会列出来。
出路是在目标表加一个「关联数据」字段指向被引用表（一次 GUI 操作，无表单结构 API），
关系即可完整同步。官方也提供「选择数据 → 关联数据」的迁移路径。

## 子表单与附件：能搬了，但边界要先说清楚

2026-09-01 打通。**先把下面这几条念给用户，再动手**——它们不是脚注，
是会真的改变结果的东西。

**子表单 = 整表替换。** 简道云的接口只有整表替换，没有行级增量：源端有任何差异，
目标端那个子表单就被**整块重写**。所以——

- 目标端子表单里的人工改动（只在目标端加的行、改的值）**会被源端覆盖**，
  计划输出会专门提示这一条
- 内层字段按**显示名**对应。对不上的逐个报出来，格式是「子表单名.内层名」
- 内层的**关联数据、附件、嵌套子表单 v1 不搬**（引用翻译和附件搬运不下沉到内层），
  整列报出理由。⚠️ 这意味着"整列搬了"不等于"整块都搬了"——
  转述时要把内层排除清单一起念，别让用户以为明细全同步了
- 可搬内层字段**全为空的子行会被丢掉**：实测简道云自己就会吞掉全空子行
  （提交 3 行回读 2 行）。丢了会报出来，多半是那几行的数据都在被排除的内层字段里

**附件 = 真的下载再上传。** 读回来只有带过期戳的 url，写入要的是重新上传拿到的 key——
附件是唯一一个"搬运必须过一遍本地磁盘"的字段类型。所以——

- 计划阶段会报出**要搬几个文件、多大**。大表可能是几个 G、几十分钟，
  这个数字要念给用户听，别让他点完 `--execute` 才发现
- 比对按 **(文件名, 大小)**。url 每次读回来都不一样（过期戳），比它等于每次全量重传。
  代价是**"内容变了但文件名和大小都没变"检测不到**——这条要如实说，不要假装能测
- 某一行的附件下载或上传失败 → **整行扣下不写**，并点名报出。
  不会留下"别的字段都在、附件列是空的"那种半条记录
- 重跑是安全的：已经一致的行判"无变化"，**一个文件都不会重传**

**只在同类之间搬**：子表单↔子表单、附件↔附件（图片和附件算同类）。
子表单↔文本这种跨类转换不做，会报出来——那是另一个功能，不该在同步里悄悄发生。

## 三件事决定同步对不对

**引用拓扑序**：被引用的表先同步，否则翻译引用时目标端还没有对应记录。
配置里 `refs` 声明了依赖，引擎自动排序；成环会报错而不是随便挑个顺序。

**ID 映射持久化**：源端与目标端是两套 data_id，靠映射表打通。
它同时是断点续跑和增量同步的基础。**按业务键匹配上的记录也会登记**——
只登记新增的是错的：第二次同步时全是"无变化"，映射表空了，所有引用都翻译不出来。
映射表写不下去时会明确警告，因为那意味着下次会把已同步的当新增重写一遍。

**引用自校验**：关联数据写入时**接口不校验引用是否存在**，写个不存在的 ID
照样入库、回读还"一致"——**连回读比对都兜不住**。所以翻译不出来的引用**不写**，
宁可留空让人看见。

## 业务键必须真的唯一

整套同步的前提是「业务键唯一标识一条记录」。前提破了，"按键匹配"就不是匹配，是猜。

计划阶段会**点名列出重复键**（连记录 ID 一起报）：

- **目标端重复** → 只有第一条会被更新，其余永远同步不到，两边越漂越远
- **源端重复** → 它们会依次写向同一条目标记录，后一条覆盖前一条

看到这个先别急着 `--execute`，**把重复念给用户听**，让他决定是去重还是换一个键。

另外：草稿默认带 `limit`（小范围试水），此时**合计数字不是全量差异**——
计划输出会明说。要给用户全量结论，先把 limit 去掉再跑一次。

## 安全边界

- **写入白名单**：若用户设了 `JDY_WRITE_ALLOWLIST`，写入目标不在名单里会被直接拒绝。
  报错里会写清名单内容——**照实转述给用户**，让他自己决定是放开名单还是换目标，
  不要绕过去（也绕不过去，校验在 HTTP 出口上）

- **默认 dry-run**，先出差异计划
- **非交互环境拒绝写入**（退出码 4）。Agent 平台里 stdin 不是 tty，
  "问不了"不等于可以替用户决定。先把计划复述给用户、取得同意，再加 `--yes`
- **写前备份目标表**到 JSON，备份失败即中止
- **写后回读核对**，静默丢字段会如实报出——**有丢字段就不要说"已完整同步"**
- **大批量另有一道闸门**：改动超过 50 条时，即使给了 `--yes` 也会被拦下（退出码 5），
  要求带上本次的**计划确认码**重跑
- `--only <alias>` 可只同步某张表，便于分批推进

### 关于计划确认码

**跟用户只谈「同步多少条」，不要谈「阈值」也不要提这个码。**
用户脑子里只有一个数字——要搬多少数据，那是配置里的 `limit`（省略即全量）。
`--confirm-threshold` 是内部安全默认值，**只能往小调**（往大调不了：一个安全机制不该由它自己的参数解除）。几乎不需要动；把它拿去问用户，
只会让人在两个数字之间犯迷糊。

撞上闸门时正确的说法是：「这次要往目标应用写入 21 条数据，确认执行吗？」
拿到同意后自己带码重跑即可。

它**拦不住你**——你读得到脚本输出，自然也能把码传回来。它保证的是另一件事：
**被确认的计划和被执行的计划是同一个**。码由目标应用、各表增改条数与业务键算出，
源数据在两次调用之间变了（多了几百条、键对不上了），码就失效，强制重新规划再确认。

所以正确用法是：**把拦截提示里的规模念给用户、取得同意，再带码重跑**。
拿到码就直接重跑而不告知用户，等于把这道闸门变成一句空话——
它的全部价值就在于让"大批量写入"这个决定被人看见一次。

## 已知边界（Beta）

- 只做**单向**同步（源 → 目标），不做双向合并与冲突解决
- 只按**业务键**判断记录同一性，业务键为空的记录会被拦下报 `missing_key`
- 增量目前靠"业务键匹配 + 值比对"，尚未使用 `updateTime` 游标
- **源端把某个字段清空了，目标端不会跟着清空**——同步只写有值的字段。
  要清空请在目标端自己改
- 子表单与附件已打通（见上一节），但 v1 明确不做这几件事：
  - 子表单**内层**的关联数据翻译、内层附件搬运、嵌套子表单——整列排除并报出理由
  - 附件"内容变了但文件名和大小都没变"检测不到（比对键是 (name, size) 的固有限制）
  - 子表单没有行级增量：目标端子表单里的人工改动会被源端整块覆盖
  - 子表单的 Excel 表达（导入导出）不在本技能里——二维表格装不下一对多，
    那是 jdy-excel-bridge 的另一个话题

## 呈现建议

- 先讲结论："要新增 120 条、更新 8 条，但有 2 个字段搬不过去"
- **搬不过去的字段一定要点名**，并说清原因和出路（换成关联数据字段）
- 同步后如实转述回读核对结果，不要笼统说"完成"
