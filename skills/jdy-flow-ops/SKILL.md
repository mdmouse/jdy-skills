# jdy-flow-ops 流程运营

## 不可绕过的规则（不管你用什么方式写入）

这几条是**对你的约束**，不是对某个脚本的说明。你完全可以自己写代码调接口——
但下面这些必须照做，因为它们保护的是用户的数据，不是我的工具：

1. **批量写入前必须向用户报条数并取得同意。** 改动超过 50 条尤其如此。
   澄清"改哪张表""按什么规则"不算取得同意——那是问需求，不是问授权。
   实测中发生过：Agent 自己写脚本，一次改了 180 条**全程没问过用户一句**。
   走本技能的 `act.py` 会被确认集闸门强制拦下；自己写就没人拦你，所以这条得你自己守。
2. **写前必须整表备份，备份失败就不要写。**
3. **写后必须回读核对**，并**如实转述**：哪些字段提交了却入库为空。
   简道云的写接口几乎不校验，脏值会静默存成 null 并返回成功。
4. **绝不删除数据——用户明说要删也不行，让他自己在简道云界面删。**
   「处理掉」「清理掉」「去重」「把重复的删了」这类说法**不构成删除授权**：
   重复不等于错误，而你判断"哪条是副本、哪条是正主"的依据往往只是先来后到，
   删错了不可逆。正确做法是**只打标记**（追加式写进备注一类的字段），
   然后告诉用户按这个标记在界面里筛出来自行删除。
   **更不要摆一个「删除」选项让用户点。** 实测中发生过：Agent 把「删除重复行」
   放在选项第一项，用户点了，2 条记录当场消失——它自己写了个 delete.py，
   本技能的脚本根本没参与。选项里只能有"只标记"，删除不是可选项之一。
5. 用户设了 `JDY_WRITE_ALLOWLIST` 时，写入目标不在名单里就停下并如实告诉他。

**能用本技能的脚本就用**——上面五条它已经替你做了，还多一层规模闸门与
只写目标列的保证。自己写不是不行，但这五条一条都不能少。

## 与官方简道云 AI 连接的分工

用户那台机器上可能同时装着**官方「AI 连接」连接器**（原 MCP 服务，2026-09-01 更名，
【官方声称】已上架 WorkBuddy／千问办公连接器市场）和本技能。两者不是二选一，
但分工是死的：

- **查数、问答、看结构——走官方连接器没问题。** 它读得快，走的是成员本人的权限，
  用户问一句「这张表有多少行」，不必绕到脚本来。
- **同意／否决／回退／转交，以及催办推送——必须走本技能的脚本。**
- **点名禁止一件事：把 AI 连接的 `member_data_create`（单条新增）循环起来当批量用。**
  AI 连接的 12 项工具里，`member_workflow_task_list` **只能列待办、不能审批**，
  催办更是一项都没有——它替代不了本技能。这里仍然点名 `member_data_create`，
  是因为它是那 12 项里唯一的写工具，也最容易被当成「官方许可的批量入口」；
  拿它去「新增一条审批记录」不会推动任何流程，只会往表里塞脏数据。

三条理由，缺一条这条禁令就退化成「因为我说了算」：

1. **它静默失败，而且没有回读。** `member_data_create` 与 REST 写接口同源——
   脏值不报错，静默存成 null 再返回成功。循环跑完你会收到 N 个「成功」，
   而用户表里那几列是空的。本技能每次写入都做**写后回读比对**，就是为了把这个抓出来。
2. **它没有备份，写错了回不去。** 本技能写前整表备份、备份失败就不写；
   连接器那条路上没有这一步，错了只能一条条手工改。
3. **它的写权限要管理员审核，数据范围还只有授权成员本人。**
   AI 连接走的是**成员个人视角**，`member_data_create` 需成员向管理员申请审核后方可用；
   半路被拒会留下一批写了一半的数据——比全失败更难收拾。

dry-run、非交互拒绝、写后回读核对、每次操作留审计日志——
这几道闸只长在本技能的脚本上。绕过脚本，等于闸门一道都不在。

一句话：**读可以借官方的手，写只走这里。**

## 四个脚本

```
python3 scripts/inbox.py                                   # 待办收件箱
python3 scripts/backlog.py --app <app_id> --entry <entry_id>   # 积压扫描
python3 scripts/nudge.py --app <app_id> --entry <entry_id>     # 催办（默认只预览）
python3 scripts/act.py approve                             # 批量处理（默认 dry-run）
```

## 先解决成员编号

**接口只认成员编号（`sys_xxx`），传显示名会报 `1010 用户不存在`。**
用户嘴里说的永远是"我的待办""张三的待办"，所以脚本会：

1. `--user` 传的若已是 `sys_`／`jdy-` 开头，直接用
2. 否则从各表单数据的 `creator`／成员字段里反查「姓名 → 成员编号」
3. 重名时**列出候选让用户挑**，绝不替他选——挑错就是把别人的待办批了

简道云没有可用的通讯录接口，所以这个索引只覆盖**在数据里出现过的人**。
常用的话建议在 `~/.jdy/config.json` 里加一行 `"username": "sys_xxx"`，省去每次解析。

## 待办收件箱

```
python3 scripts/inbox.py --group-by form      # 也可 creator / node
python3 scripts/inbox.py --json-out tasks.json
```

按数量降序分组，组内按等待时长降序——**最该先处理的排在最前**。
末尾点出等最久的那条。`--json-out` 的产物可直接交给 `act.py` 批量处理。

**每条待办会带上业务内容**（申请标题、金额、数量等）。这不是锦上添花：
`task/list` 只返回元数据，同一张表单的多条待办在列表里长得**一模一样**，
而人指代审批永远靠内容——"把那条五万的批了""退回缺料的那几条"。
没有内容就没法把人话对应到具体待办。嫌慢可以 `--no-detail` 关掉。

`--contains 关键词` 按内容筛选。

## 积压扫描

```
python3 scripts/backlog.py --app A --entry E --threshold 24
```

`instance_id` 等同 `data_id`，所以从表单数据就能枚举流程实例；
每个实例的 `tasks[]` 带每个节点的 `create_time`／`finish_time`，
据此算出**当前卡住的待办**（超阈值的标红）与**各节点平均/最长耗时**，给出瓶颈节点。

**「没有流程实例」通常不是故障**：流程配好之前就存在的数据不会补建实例，
只有此后新提交的记录才走流程。看到这个结论要这样解释，别让用户以为坏了。

## 催办

简道云**没有催办 API**，界面上的催办也只能一条一条点。而积压扫描已经算得出
"卡在谁手上、卡了多久"——差的只是把它说成一句人看得懂的话，再发出去。

```
python3 scripts/nudge.py --app <应用> --entry <表单> --threshold 24     # 只汇总
python3 scripts/nudge.py --app A --entry E --webhook <URL>              # 预览要发什么
python3 scripts/nudge.py --app A --entry E --webhook <URL> --send --yes # 确认后真发
```

**按人汇总，不按条列。** 一条一条列出来，群里刷屏且没人对号入座；
按人汇总，每个人一眼看到"我有 3 条，最久的等了 5 天"，这才叫催办。
每人最多列 3 条，其余折成"…另有 N 条"。

**消息里不含业务内容。** 催办是发到群里的，收件人不止当事人——只说
哪个流程、哪个节点、卡了多久，不带申请标题和金额。

⚠️ 和推报表同一条规矩：**默认只预览**，`--send` 才真发，非交互环境没有 `--yes`
直接拒绝（退出码 4）。发出去收不回，而催办是一次性 @ 到一群人。
`--check` 只验 webhook 通不通、**不发任何消息**（只发 GET，群里不留痕）。

webhook 缺省读环境变量 `JDY_REPORT_WEBHOOK`，和 jdy-report 共用一个。

## 批量处理

```
# 1) 先把清单固化下来，再对着这份清单操作——别让两次调用各拉各的
python3 scripts/inbox.py --contains 请假 --json-out tasks.json
python3 scripts/act.py approve --tasks-json tasks.json          # dry-run，末尾给出确认码
python3 scripts/act.py approve --tasks-json tasks.json --execute --yes --confirm-code <码>

python3 scripts/act.py reject --comment "预算不足" --execute --yes --confirm-code <码>
python3 scripts/act.py transfer --transfer-to 张三 --execute --yes --confirm-code <码>
python3 scripts/act.py rollback --comment "补充材料" --back-type 1 --execute --yes --confirm-code <码>
```

**为什么推荐先 `--json-out` 再 `--tasks-json`**：不给 `--tasks-json` 时，
dry-run 与 `--execute` 会**各自实时重拉一遍待办**，两次之间新到的待办
会一起被处理——用户点头的是 3 条，执行的是 5 条。固化清单让两次看的是同一份。

筛选：`--contains` 按**业务内容**匹配（最贴近用户说法）、`--form`／`--node` 按名称匹配、
`--task-id` 指定具体待办（可重复）。

**用户说的关键词多半是内容而不是表单名**——比如"那几条流程验证的"指的是申请标题里的字，
表单其实叫「缺货申请」。找不到时先用 `inbox.py` 看清内容再定，不要拿相近的表单顶替。

⚠️ **写操作的铁律**：

- **默认 dry-run**，先把会动哪些逐条列出来；dry-run 末尾会给出本批的确认码
- **`--execute` 必须带 `--confirm-code`**（不分批量大小）。码由这一批的 `task_id` 集合算出，
  清单一变即失效——保证用户点头的那批，和真正执行的那批是同一批
- **非交互环境直接拒绝**（退出码 4）。Agent 平台里 stdin 不是 tty，
  "问不了"不等于可以替用户决定。正确做法是**把清单复述给用户、取得明确同意**，再加 `--yes`
- **审批不可自动撤销**，比导入数据更需要谨慎——导错了还能删，批错了流程已经往下走了
- 每次操作写审计日志（谁、何时、对哪条、结果如何）。落点是**运行时探出来的**：
  优先 `$JDY_HOME`，再 `~/.jdy`，再宿主自己的配置目录，再会话工作目录。
  各端沙箱的写白名单不同（WorkBuddy 实测不放行 `~/.jdy`），所以别去固定位置找——
  执行完屏幕上会打印实际路径。一个可写目录都没有时会明说「操作已执行但没有留痕」
- **写后自动核对**：重新读实例，确认节点状态真的从「待处理」变了。
  接口回报成功不等于状态变了——简道云在别处已多次出现"回报成功但什么都没发生"。
  **核对不通过的条目，不要向用户报"已处理"**，如实说明并让其去界面确认
- 否决**可能**要求 `--comment`（取决于节点配置）；要求而没给会报 `5004 No comment for approval`
- **回退与转交需要在简道云流程设计里先开启**，否则报 `50040` / `5049`。
  这是配置问题不是故障——要这样告诉用户，并指明去哪开。
  **收到这两个码就不要再调参数了**：`back_type`／`flow_id` 只在回退已启用时才起作用，
  节点没开的话换什么参数都是同一个错。正确的下一步是告诉用户
  「去流程设计里给该节点开启回退／转交」，或者改用能用的操作（如否决并说明原因）

## 呈现建议

- 先说结论："有 12 条待办，3 条超过一天没动"，再列细节
- **等待时长并列时，用业务内容判断优先级**——脚本只按时长排序，
  谁更急要看内容（金额、数量、紧急程度这类字段就在每条待办下面）。
  技能负责把内容摆出来，判断由你来做
- 积压扫描要点出**瓶颈节点**和**卡了谁**，而不只是罗列数字
- 批量操作前把清单念给用户听，**特别是发起人是谁**——批的是别人的申请

## 安全边界

- **写入白名单**：若用户设了 `JDY_WRITE_ALLOWLIST`，写入目标不在名单里会被直接拒绝。
  报错里会写清名单内容——**照实转述给用户**，让他自己决定是放开名单还是换目标，
  不要绕过去（也绕不过去，校验在 HTTP 出口上）

读操作只调 `task/list`、`instance/get`。写操作见上。
密钥读 `JDY_API_KEY` 或 `~/.jdy/config.json`，绝不写进技能目录。
