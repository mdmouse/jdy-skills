# jdy-excel-bridge Excel ⇄ 简道云

## 不可绕过的规则（不管你用什么方式写入）

这几条是**对你的约束**，不是对某个脚本的说明。你完全可以自己写代码调接口——
但下面这些必须照做，因为它们保护的是用户的数据，不是我的工具：

1. **批量写入前必须向用户报条数并取得同意。** 改动超过 50 条尤其如此。
   澄清"改哪张表""按什么规则"不算取得同意——那是问需求，不是问授权。
   实测中发生过：Agent 自己写脚本，一次改了 180 条**全程没问过用户一句**。
   走本技能的 apply.py 会被规模闸门强制拦下；自己写就没人拦你，所以这条得你自己守。
2. **写前必须整表备份，备份失败就不要写。**
3. **写后必须回读核对**，并**如实转述**：哪些字段提交了却入库为空。
   简道云的写接口几乎不校验，脏值会静默存成 null 并返回成功。
4. **绝不删除数据——用户明说要删也不行，让他自己在简道云界面删。**
   「处理掉」「清理掉」「去重」「把重复的删了」这类说法**不构成删除授权**：
   重复不等于错误，而你判断"哪条是副本、哪条是正主"的依据往往只是先来后到，
   删错了不可逆。正确做法是**只打标记**（追加式写进备注一类的字段），
   然后告诉用户按这个标记在界面里筛出来自行删除。
   **更不要摆一个「删除」选项让用户点。** 实测中发生过：Agent 把「删除重复行」
   放在选项第一项，用户点了，2 条记录当场消失——它自己写了个 delete.py，
   本技能的脚本根本没参与。选项里只能有"只标记"，删除不是可选项之一。
5. 用户设了 `JDY_WRITE_ALLOWLIST` 时，写入目标不在名单里就停下并如实告诉他。

**能用本技能的脚本就用**——上面五条它已经替你做了，还多一层规模闸门与
只写目标列的保证。自己写不是不行，但这五条一条都不能少。

## 与官方简道云 AI 连接的分工

用户那台机器上可能同时装着**官方「AI 连接」连接器**（原 MCP 服务，2026-09-01 更名，
【官方声称】已上架 WorkBuddy／千问办公连接器市场）和本技能。两者不是二选一，
但分工是死的：

- **查数、问答、看结构——走官方连接器没问题。** 它读得快，走的是成员本人的权限，
  用户问一句「这张表有多少行」，不必绕到脚本来。
- **批量导入、导入后的修复回写、附件上传、导出改完再更新回去——必须走本技能的脚本。**
- **点名禁止一件事：把 AI 连接的 `member_data_create`（单条新增）循环起来当批量用。**
  这正是最像「用官方工具也能做」的那一件：一个 3 行的小 Excel，循环三次就导完了，
  看着毫无问题。但预检、分批幂等、写后回读比对全没经过——
  而被静默丢掉的列，恰恰只有回读才看得见。

三条理由，缺一条这条禁令就退化成「因为我说了算」：

1. **它静默失败，而且没有回读。** `member_data_create` 与 REST 写接口同源——
   脏值不报错，静默存成 null 再返回成功。循环跑完你会收到 N 个「成功」，
   而用户表里那几列是空的。本技能每次写入都做**写后回读比对**，就是为了把这个抓出来。
2. **它没有备份，写错了回不去。** 本技能写前整表备份、备份失败就不写；
   连接器那条路上没有这一步，错了只能一条条手工改。
3. **它的写权限要管理员审核，数据范围还只有授权成员本人。**
   AI 连接走的是**成员个人视角**，`member_data_create` 需成员向管理员申请审核后方可用；
   半路被拒会留下一批写了一半的数据——比全失败更难收拾。

逐格预检、分批幂等提交（`transaction_id`）、规模闸门、写前整表备份、写后回读比对、
`JDY_WRITE_ALLOWLIST` 写入白名单、dry-run、非交互拒绝——这几道闸只长在本技能的脚本上。
绕过脚本，等于闸门一道都不在。

一句话：**读可以借官方的手，写只走这里。**

## 先记住一件事

日期列请尽量用 `YYYY-MM-DD`。`2026/08/27` 会被自动归一化，
但 `01/12/2025` 这种**日/月都可能**的写法会被拒绝并要求改写——
猜错一次整列就错了几个月，而且写进去之后看不出来。

**简道云的写入接口几乎不校验。** 日期写成 `2026/08/27`、数字写成 `abc`、值的格式包错一层——
全部返回 `success`，然后把该字段静默存成 `null`。接口里**没有"失败行"这个概念**。

所以本技能的工作流不是"导入→看报错"，而是：

```
preflight 预检  →  用户确认  →  分批写入  →  回读比对  →  修复建议表
```

**回读比对不能跳过**。跳过它，就等于告诉用户"导入成功了"，而实际上整列是空的。

## 第一步：先把表定位准

用户说的是「某某应用的某某表」，脚本要的是 `app_id` / `entry_id`。**不要自己猜、
不要去翻 `~/.jdy/cache/`**（那里只有字段信息，没有表单名，拼不出完整清单）。

```
python3 scripts/export.py --list                    # 列出所有应用
python3 scripts/export.py --app <应用名或ID> --list       # 列出该应用的表单 + 行数
```

`--app` / `--entry` **直接写名字就行**，脚本会解析成 ID：

```
python3 scripts/export.py --app <应用名或ID> --entry <表单名或ID> --out 导出.xlsx
```

名字对上多个目标时脚本会把候选列出来并拒绝执行——**这时才需要问用户**。
问之前一定先跑 `--list`：不同应用里可能有同名表单，凭印象给菜单会漏掉正确答案。

## 导入

```
python3 scripts/preflight.py 数据.xlsx --app <应用名或ID> --entry <表单名或ID> --plan plan.json
```

**时区**：默认按 `+08:00`（北京时间）解释 Excel 里的时间——简道云界面按 +8 显示，
中文用户的表格默认就是北京时间。源数据是别的时区就加 `--tz utc` / `--tz -04:00`。
**不要用 `--tz local`**，除非确认跑脚本的机器时区就是数据时区：否则同一份 Excel
在不同机器上会落成不同的值，而且界面上看不出任何异常。

预检输出四类信息，逐条念给用户听：

1. **字段映射**——每列匹配到哪个字段、怎么匹配上的。标了「⚠️ 模糊匹配」的**必须让用户确认**
2. **导不进去的列**——`linkdata` 关联字段接口不支持写入、`sn` 流水号系统生成。
   这类列写了也是空的，**要在导入前说，不是导完才说**
3. **两侧对不上的列**——Excel 有表单没有（会被静默忽略）、表单有 Excel 没提供
4. **数据问题**——逐格类型校验的结果，带行号和原值。
   **有问题的行整行扣下不写**，避免写出缺字段的记录、也避免用户改完再导产生重复行

用户确认后：

```
python3 scripts/import_data.py plan.json                       # dry-run，看看会发生什么
python3 scripts/import_data.py plan.json --execute --fix-sheet 修复建议.xlsx
```

`--execute` 会先自动备份整表到 JSON，备份失败就中止——没有备份不动数据。
写入后自动回读比对，报告哪些字段提交了但入库为空。

⚠️ **`--execute` 在非交互环境下会拒绝执行**（Agent 平台里 stdin 不是 tty，脚本没法当面问用户）。
正确做法：**先把 dry-run 的结果复述给用户、拿到明确同意**，再加 `--yes` 重跑。
不要一上来就 `--execute --yes` —— 那等于替用户做了写入决定。

**修复循环**：把修复建议表给用户 → 用户改 Excel → 重跑 preflight → 再导。
被扣下的行不会进第一轮，所以第二轮只补这几行，不会重复。

## 导出

```
python3 scripts/export.py --app <应用名或ID> --entry <表单名或ID> --out 导出.xlsx
python3 scripts/export.py --app A --entry E --out o.xlsx --where '_widget_123=待处理;_widget_456:gt:100'
```

条件写法：`字段标识=值`（多条用 `;` 连接，关系为 and），或 `字段标识:method:值`。
method 可用 `eq ne in nin range like gt lt empty not_empty verified unverified all`。
不知道字段标识就先用 `jdy-doc` 导一份数据字典。

## 附件：连文件一起进出

附件默认**只导文件名**，因为附件 URL 带过期戳（实测约 15 天）——把 URL 放进
表格，用户过两周点开全是死链。要连文件一起导出：

```
python3 scripts/export.py --app A --entry E --out 导出.xlsx --attachments ./附件
```

文件落到 `./附件/<记录ID>/<列名>/`，**一条记录、一列一个子目录**，单元格里写
相对路径（多个文件用 ` | ` 分隔）。同一格里有两个同名文件时再多分一层序号目录。

分目录是有原因的：附件名是用户上传时的原名，重名很正常，而堆在一个目录里就得靠
`-2`、`-3` 后缀去重——导回时是**按文件名**判断这一格改没改的，被改过名的文件
永远对不上，于是每次原样导回都会把那几行的附件重传、记录重写一遍。
三种重名都要挡住，少挡一种就等于没挡：

| 重名 | 例子 | 挡它的是 |
|---|---|---|
| 跨记录 | 两条记录各有一个「合同.pdf」 | `<记录ID>/` 这一层 |
| 跨列 | 同一条记录的两个附件列各有一个「合同.pdf」 | `<列名>/` 这一层 |
| 格内 | 同一格里传了两个同名文件（简道云允许） | 再多一层序号目录 |

**落盘的文件名永远等于库里的名字**，不会被改。顺带也一眼看得出哪个文件属于
哪条记录的哪一列。

反过来，**附件列填本地文件路径就能导进去**：

| 岗位 | 合同查看 |
|---|---|
| 销售 | `附件/合同A.pdf` |
| 研发 | `附件/合同B.pdf \| 附件/图纸.png` |

（自己新建的表随便放哪个目录都行；导出产生的表里则是 `附件/<记录ID>/xxx`。）

**原样导回不会重传。** 附件列按**文件名**比对：导出的这一格和库里是同一批文件，
就判定没变、跳过这一行。换个文件、少一个文件、清空，都算真的改了。
只比文件名不比内容——本地文件换了内容但没改名，会被当成没改；
要强制重传就把文件改个名。

相对路径按 **Excel 所在目录**算。预检会先确认文件在不在，找不到的行**扣下**
（`file_missing`）——留到上传时才发现，前面的行已经写进去了，只能补第二遍。

⚠️ **带附件一次最多 100 行。** 附件上传的凭证绑定在一个事务号上，而分块写入时
每块必须用不同的事务号（相同的会互相覆盖），所以两者不能兼得。超了会直接报错
要你拆开分次导——不会默默拆块，那会让后面几块的附件全部失效而接口照样回报成功。
这条只限**新增**：更新是逐条写的，每行各用一个事务号，不受 100 行限制。

**更新（带 `_id` 那条路）同样能换附件**——下面「改完导回去」讲的正是这条路。
早前只有新增会上传文件，更新那半直接把本地路径当成上传后的 key 提交，
接口回报成功、附件却是空的（回读核对会标出来，但附件就是搬不动）。现在两边一样。

## 改完导回去（导出 → 编辑 → 更新原记录）

导出带 `_id` 列，**这一列就是回写的定位依据**：

| `_id` 这一格 | 行为 |
|---|---|
| 保持导出时的值 | **更新**那条记录（局部更新，没在表里的字段不会被清空） |
| 留空 / 整列不存在 | 新增 |
| 填了但不是 24 位十六进制 | 整行扣下，**不会降级成新增** |
| 格式对但目标表里没有 | 整行扣下——可能记录已删除，或这个 `_id` 来自别的表单 |

所以「导出改几行再导回去」是完整支持的，走的还是同一条链路：

```
export.py → 用户在 Excel 里改 → preflight.py → import_data.py --execute
```

**要提醒用户：不要删 `_id` 列，也不要动里面的值。** 删了就全变成新增，
一份 22 行的表会再写 22 条重复记录——接口不会拦。

`创建时间` 列是导出附带的系统列，导入时自动忽略，不用管。

**没改的行会自动跳过。** 导出全表、只改两行、整份导回，预检只会更新那两行——
其余行值与库里一致就不重复写。每一次写入都是一次静默丢字段的机会，没改就别写。

## 用脚本批量改 Excel

「把某批行的某列统一改成 X」别手改，写脚本——但**用技能自带的 xlsx 模块**。
沙箱里通常没有 openpyxl，也装不了；自带实现零依赖，且导出/导入两侧都走它，格式一致。

```python
import sys
sys.path.insert(0, "<本技能目录>/scripts")
import _bootstrap                      # 必须：把 scripts/_shared 挂进 sys.path
from xlsx import read_rows, write_sheet
```

两个读函数**返回形状不同**，很容易踩：

| 函数 | 返回 |
|---|---|
| `read_rows(path)` | `list[list]`，**第 0 行是表头** |
| `read_table(path)` | **元组** `(headers, list[dict])`——不是 `list[dict]` |

`write_sheet(path, headers, rows)` 的 `rows` 是 `list[list]`，与 `read_rows` 对齐，
所以「读→改→写」用 `read_rows` + `write_sheet` 最省事。

**只把要改的行写进回写文件，比整表导回更稳**：预检输出短、写入面小，
也不会因为整表里某行的历史脏值被顺带重写。

## 呈现建议

- 复述计划时**照抄预检给的行标识**（「第 6 行 王先生 / 13222222222」），
  不要自己去文件里数行补充"那行是谁"——实测里这样数错过一行，
  差点让用户对着错的记录拍板
- 预检结论**先说结论再说细节**："这份表能导，但『客户信息』列导不进去" 比逐条罗列有用
- 数据问题多时按类型归组说，别把 200 行错误全铺进对话
- 导入后必须**如实转述回读结果**。回读发现静默丢字段，就是没导成功，不要说"导入完成"
- 更新和新增要**分开说**："更新了 3 条、新增了 1 条"，别笼统说"导入了 4 条"

## 安全边界

- **写入白名单**：若用户设了 `JDY_WRITE_ALLOWLIST`，写入目标不在名单里会被直接拒绝。
  报错里会写清名单内容——**照实转述给用户**，让他自己决定是放开名单还是换目标，
  不要绕过去（也绕不过去，校验在 HTTP 出口上）

- **改动超过 50 条会被拦下**，要先把条数说给用户、拿到同意，再带确认码重跑。
  确认码由计划内容算出，源数据一变即失效——保证用户点头的计划就是执行的计划。
  跟用户说「这次要写入 N 条，确认吗？」就行，**别提「阈值」或这个码**。
  **码在 dry-run 阶段就会打印**——先拿码、再取得同意、最后才 `--execute`，
  不需要（也不应该）为了拿码先试着写一次
- 写入默认 dry-run，`--execute` 才真写；交互环境下还会二次确认
- 写前强制整表备份，备份失败即中止
- 分块 ≤100 条，每块带 `transaction_id`，重试不会产生重复数据
- 密钥读 `JDY_API_KEY` 或 `~/.jdy/config.json`，绝不写进技能目录
