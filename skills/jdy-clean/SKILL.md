# jdy-clean 存量数据清洗

## 不可绕过的规则（不管你用什么方式写入）

这几条是**对你的约束**，不是对某个脚本的说明。你完全可以自己写代码调接口——
但下面这些必须照做，因为它们保护的是用户的数据，不是我的工具：

1. **批量写入前必须向用户报条数并取得同意。** 改动超过 50 条尤其如此。
   澄清"改哪张表""按什么规则"不算取得同意——那是问需求，不是问授权。
   实测中发生过：Agent 自己写脚本，一次改了 180 条**全程没问过用户一句**。
   走本技能的 apply.py 会被规模闸门强制拦下；自己写就没人拦你，所以这条得你自己守。
2. **写前必须整表备份，备份失败就不要写。**
3. **写后必须回读核对**，并**如实转述**：哪些字段提交了却入库为空。
   简道云的写接口几乎不校验，脏值会静默存成 null 并返回成功。
4. **绝不删除数据——用户明说要删也不行，让他自己在简道云界面删。**
   「处理掉」「清理掉」「去重」「把重复的删了」这类说法**不构成删除授权**：
   重复不等于错误，而你判断"哪条是副本、哪条是正主"的依据往往只是先来后到，
   删错了不可逆。正确做法是**只打标记**（追加式写进备注一类的字段），
   然后告诉用户按这个标记在界面里筛出来自行删除。
   **更不要摆一个「删除」选项让用户点。** 实测中发生过：Agent 把「删除重复行」
   放在选项第一项，用户点了，2 条记录当场消失——它自己写了个 delete.py，
   本技能的脚本根本没参与。选项里只能有"只标记"，删除不是可选项之一。
5. 用户设了 `JDY_WRITE_ALLOWLIST` 时，写入目标不在名单里就停下并如实告诉他。

**能用本技能的脚本就用**——上面五条它已经替你做了，还多一层规模闸门与
只写目标列的保证。自己写不是不行，但这五条一条都不能少。

## 与官方简道云 AI 连接的分工

用户那台机器上可能同时装着**官方「AI 连接」连接器**（原 MCP 服务，2026-09-01 更名，
【官方声称】已上架 WorkBuddy／千问办公连接器市场）和本技能。两者不是二选一，
但分工是死的：

- **查数、问答、看结构——走官方连接器没问题。** 它读得快，走的是成员本人的权限，
  用户问一句「这张表有多少行」，不必绕到脚本来。
- **批量规范化回写、去重打标、分类与信息提取的批量回写——必须走本技能的脚本。**
- **点名禁止一件事：把 AI 连接的 `member_data_create`（单条新增）循环起来当批量用。**
  清洗回写改的是**已有记录**，而 `member_data_create` 只能新增——
  拿它「重建一份干净的」，等于给用户凭空多出一批重复数据，原来那批还在。

三条理由，缺一条这条禁令就退化成「因为我说了算」：

1. **它静默失败，而且没有回读。** `member_data_create` 与 REST 写接口同源——
   脏值不报错，静默存成 null 再返回成功。循环跑完你会收到 N 个「成功」，
   而用户表里那几列是空的。本技能每次写入都做**写后回读比对**，就是为了把这个抓出来。
2. **它没有备份，写错了回不去。** 本技能写前整表备份、备份失败就不写；
   连接器那条路上没有这一步，错了只能一条条手工改。
3. **它的写权限要管理员审核，数据范围还只有授权成员本人。**
   AI 连接走的是**成员个人视角**，`member_data_create` 需成员向管理员申请审核后方可用；
   半路被拒会留下一批写了一半的数据——比全失败更难收拾。

规模闸门、写前整表备份、写后逐字段回读、`JDY_WRITE_ALLOWLIST` 写入白名单、
dry-run、非交互拒绝——这几道闸只长在本技能的脚本上。绕过脚本，等于闸门一道都不在。

一句话：**读可以借官方的手，写只走这里。**

## 先记住两件事

**一、清洗改的是存量数据，错了没有退路。**
新增写错了可以不管那条新记录；清洗写错了，原值已经没了。
所以这里的闸门比别处密：写前强制整表备份（失败即中止）、
大批量要确认码、非交互环境拒绝执行、写后逐字段回读核对。

**二、这个技能不删数据。**
重复 ≠ 错误——同名两人、同号两单都可能是真的。
去重只把重复组**摆出来并打标记**，删哪条是业务判断，必须由人在界面上做。
用户要是说"帮我把重复的删了"，照实告诉他：本技能只标不删，
标完他可以在简道云里按标记筛选、自己确认后删除。

## 工作流程

```
scan.py 看现象  →  念给用户听  →  plan.py 出计划  →  用户确认  →  apply.py 执行
```

### 一、扫描（只读）

```
python3 scripts/scan.py --list                          # 不知道表名就先列
python3 scripts/scan.py --app <应用名或ID> --entry <表单名或ID>
```

报四类**现象**：填充率、格式不统一（同一列里有几种写法）、逐值毛病、值重复。

**它只描述现象，不下业务判断。** "手机号该 11 位"是领域知识，引擎不该知道；
引擎只能说"这列 90% 是 `9{11}`，另外 10% 是 `9{3}-9{4}-9{4}`"。
哪些该修、怎么修，**拿这份扫描去问用户**。

### 二、出计划（只读）

```
python3 scripts/plan.py --app <应用> --entry <表单> --normalize 列名,列名 --plan p.json
python3 scripts/plan.py --app <应用> --entry <表单> --normalize '*' --plan p.json   # 全部文本列
python3 scripts/plan.py --app <应用> --entry <表单> \
        --dedupe 手机 --mark-field 备注 --plan p.json
```

**`--normalize` 只做不改变语义的处理**：去首尾空白、压缩连续空格、
全角字母数字转半角、去控制字符。

它**不碰全角标点**——「示例：王猛」里的全角冒号在中文里是正确写法，
改成半角是破坏数据。同理不补零、不改大小写、不猜日期格式，那些都是领域规则。

**`--dedupe` 必须配 `--mark-field`**，标记会**追加**到该列而不是覆盖
（标记列多半是「备注」这种有内容的字段），重复执行不会重复追加。

### 三、执行

```
python3 scripts/apply.py p.json                       # dry-run
python3 scripts/apply.py p.json --execute --yes       # 确认后执行
```

改动超过 50 条会被拦下，要先把条数说给用户、拿到同意再带确认码重跑。
**码在 dry-run 阶段就会打印**——先拿码、再取得同意、最后才 `--execute`。
跟用户说「这次要修改 N 条已有数据，确认吗？」就行，别提「阈值」或这个码。

### 四、写坏了怎么改回去

每次 `--execute` 之前都会在计划文件旁边落一份整表备份
（`backup_<entry_id>_<时间>.json`，清洗／同步／导入三条链路同一种命名）。

```
python3 scripts/restore.py backup_<entry_id>_<时间>.json                  # dry-run
python3 scripts/restore.py backup_<entry_id>_<时间>.json --execute --yes  # 确认后改回
```

它只改回**值有出入且记录还在**的那些行，一致的不动、备份之后新增的不碰
（本技能从不删数据）。恢复本身也是一次批量写入，所以同样先备份当前状态、
同样有规模闸门、同样逐字段回读核对。

⚠️ **已经被删掉的记录，任何工具都恢复不了**：简道云不允许指定 `data_id` 新建，
新建出来的是另一条记录、另一个 ID，指向它的关联仍然是断的。
这类记录 restore.py 会单独列出来——**不要向用户说"已完整回滚"**。

## 五、分类打标 / 信息提取

**判断由你做，技能只管校验与安全写入。** 分类口径是业务知识，引擎不该知道。

### 小批量（几十行）——默认走这条

你自己读数据、自己判断，把结果写成**一个** `{data_id: 标签}` 的 JSON，剩下交给技能：

```
python3 scripts/label.py --app <应用> --entry <表单> --target 备注信息 \
        --labels labels.json --plan p.json
python3 scripts/apply.py p.json --execute --yes
```

`--labels` 会替你把关：目标列能不能写、每个 data_id 在不在表里、
哪些留空了——然后生成计划。**写入一定走 apply.py**，那里才有
写前整表备份、规模闸门、写后逐字段回读。

> 别为了省事绕开 apply.py 自己调接口。实测中就发生过：Agent 自己写脚本写库，
> 备份、闸门、回读核对全都没了——它自己不会知道哪个字段被简道云静默丢掉了。

### 大批量（几百上千行）——分批走

行数多到你一次读不完时，用批次模式，让技能替你切：

```
python3 scripts/label.py --app <应用> --entry <表单> \
        --source 反馈内容,标题 --target 分类 --batch-size 50 --out 批次
# 逐个打开 批次-N.json，把判断填进每行的目标字段，存回原文件
python3 scripts/label.py --collect 批次-*.json --plan p.json
python3 scripts/apply.py p.json --execute --yes
```

回收时会比对**源字段快照**：被顺手改过的行一律拒绝写入。
打标只该写标签列，源数据被改了是最难发现的损坏——标签看着是对的，
没人会回头核对依据。

**为什么能突破官方 AI 节点 50 行 × 10 列的上限**：那是平台侧节点的限制，
而这里做判断的是你自己，一批多少行只取决于你的上下文，也不消耗平台点数。

两种模式回收后都会报三个数：可写入多少、**未填多少**、被拒多少。
未填的不要当成"没有分类"——如实告诉用户还剩多少没处理完。

## 呈现建议

- 扫描结果**先说最要紧的一两条**，别把十列的画像全铺进对话
- **看样例，别只看形状。** 每种写法旁边都给了一个真实值，占比过半的还标了出来。
  形状是抽象的：`中{4}-9{2}×150` 看不出是什么，样例 `'闸门测试-10'` 一眼就明白。
  实测中有一轮就是只看形状、跑去单独捞值，结果只捞到零头，
  把占 87% 的测试垃圾整个漏掉了，还得出"这张表人都在"的结论
- **形状 ≠ 错误。** `9{11}@9{3}.a{3}` 是 `13800138000@163.com`——
  用手机号做前缀的正常邮箱，不是"手机号错填进了邮箱字段"。
  同一轮实测里就这么误判过。拿不准就把样例念给用户，让他判断
- 计划要**念改动样例**（原值 → 新值），不要只报"要改 N 条"
- 执行后**如实转述回读结果**。有静默丢字段就是没清洗成功，不要说"已完成"
- 用户说"删掉重复的"时，明确说明本技能只标不删，以及标完他怎么自己删
- 打标回收后**未填的行数要说出来**，别让用户以为全部处理完了

## 安全边界

- **写入白名单**：若用户设了 `JDY_WRITE_ALLOWLIST`，写入目标不在名单里会被直接拒绝。
  报错里写清了名单内容，照实转述给用户
- 写前强制整表备份，备份失败即中止
- 默认 dry-run；`--execute` 在非交互环境下不给 `--yes` 会拒绝执行
- 写后逐字段回读核对，找出被简道云静默丢弃的字段
- 密钥读 `JDY_API_KEY` 或 `~/.jdy/config.json`，绝不写进技能目录
