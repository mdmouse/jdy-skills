# jdy-doc 数据字典与结构体检

给简道云应用做两件事：**说清楚它长什么样**（数据字典），**指出哪里有问题**（体检）。
全程只读。

## 和官方 Jander 的分工（[doc/26877](https://hc.jiandaoyun.com/doc/26877)）

Jander 的「分析已有应用、识别潜在问题」和本技能的体检看着像同一件事，实际不是：

| | Jander | jdy-doc |
|---|---|---|
| 在哪用 | 简道云平台内 | 任何 Agent 端（三端 + Claude Code） |
| 谁能用 | **仅管理员** | 任何拿得到 API Key 的人 |
| 视角 | **搭建视角**——帮你把应用建起来／改结构 | **集成视角**——这张表能不能被 API 写、能不能被 Excel 导 |
| 对存量应用 | 只读解读 | 只读解读 **＋ 落盘可交付文件** |
| 产出 | 平台内的分析结论 | **Markdown 数据字典文件**（`--json` 另存结构化副本） |

→ 用户要「把结构讲清楚、交给别人」或「查导入为什么丢数据」就用本技能；
要「新建一个应用／改表单结构」那是 Jander 的活，如实告诉他去平台里用。
两者不冲突，别去抢它的活，也别把自己的活说成它能干。

## 何时用哪个

| 用户想要 | 跑哪个 |
|---|---|
| "导出数据字典" "这个应用有哪些表和字段" "给新同事一份说明" | `export_dict.py` |
| "体检" "结构有什么问题" "为什么导入老出错" "字段是不是太乱了" | `health_check.py` |
| 两者都要 | 先体检，再导字典——体检结论写进字典开头更有用 |

## 数据字典

```
python3 scripts/export_dict.py --app <app_id> --out 数据字典.md
```

不知道 app_id 就先列出来：

```
python3 scripts/export_dict.py --list                     # 列应用
python3 scripts/export_dict.py --app <应用名或ID> --list  # 列该应用的表单与行数
```

`--app` 可直接写应用名，不必先查 ID。

产出 Markdown：应用 → 每张表单 → 字段表（显示名 / 类型 / 字段标识 / 是否可 API 写入），
子表单内部字段以缩进子表呈现。`--json` 可另存结构化副本供后续技能复用。

## 体检

```
python3 scripts/health_check.py --app <app_id>
```

逐条报告问题、涉及的表单与字段、以及**为什么这是个问题**。
加 `--samples 50` 调整孤儿字段检测的抽样行数（默认 30，抽得越多越准也越慢）。

检查项与判定依据见 `references/health-rules.md`。其中三条值得单独说：

- **不可 API 导入的关联字段**：`linkdata` 类型实测无法通过 API 写入（十种写法全部静默失败）。
  含这类字段的表单，Excel 导入时该列**必然为空且不会报错**。这是"导入成功了但数据不对"的头号成因。
- **流水号冲突风险**：`sn` 由系统生成，计数器可能与既有数据不同步，产生重复编号。
- **默认字段名**：`单行文本_1` 这种名字会让 AI 和人都认不出字段含义，也让 Excel 表头匹配失效。

## 呈现建议

- 体检结果按严重度讲，**先说影响再说现象**："这张表导入时关联列会静默丢空" 比 "存在 linkdata 字段" 有用
- 数据字典较长时，先给用户看**表单清单和问题摘要**，再问要不要看全文
- 字段多的表单（>100）不要在对话里全铺开，落成文件更合适

## 安全边界

只调用只读接口（`app/list`、`entry/list`、`widget/list`、`data/list`），不写入、不删除。
密钥读 `JDY_API_KEY` 环境变量或 `~/.jdy/config.json`，缺失时引导用户配置，**绝不写进技能目录**。
