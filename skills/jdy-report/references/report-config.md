# 报表定义写法

YAML（也接受 `.json`）。解析器是内置的 YAML 子集实现——沙箱装不了 PyYAML。

## 完整示例

```yaml
name: CRM 销售周报              # 报表标题
app: <app_id>  # 应用 ID
tz: "+08:00"                   # 可选，报表时区。见下方「tz」一节

period:
  field: 创建时间               # 周期字段。可填「创建时间」「更新时间」等系统字段，
                               # 或某个日期时间类型字段的显示名。缺省为「创建时间」
  range: last_7_days           # 见下方取值表
  compare: previous            # previous（默认）｜ none（不算环比）

sections:
  - title: 跟进记录
    entry: "<id>"   # 表单 ID；纯数字开头务必加引号
    metrics:
      - {label: 跟进次数, agg: count}
      - {label: 跟进人数, agg: distinct, field: 跟进人}
    dimensions: [跟进人]        # 可多维：[跟进人, 客户]
    top: 5                     # Top 榜条数，省略则全列
    trend: week                # day｜week｜month；省略则不出趋势表
    period_field: 跟进时间      # 可选：只给这个板块换时间轴
```

## `period_field`：按板块换时间轴

全局 `period.field` 对所有板块生效，但**各表的业务日期字段名往往不同**
（跟进记录用「跟进时间」、商机用「报备时间」、订单用「订单签订日期」）。
只有一根全局轴的话，想按业务日期看趋势就只能整份报表退回「创建时间」——
而创建时间常常是批量导入的时刻，画不出真实走势。

板块级 `period_field` 覆盖全局，一份报表里可以并存多根轴，
报表里会标出每个板块实际用的是哪一根。

## `trend`：把区间切成时间序列

只给"本期 vs 上期"两个数常常不够——用户想看的是"这 30 天每周怎么走"。
加 `trend: week` 就会在该板块下多出一张按周（或天/月）拆的表。

**空桶会保留为 0**，不是跳过。只对有数据的时间分组，会让不同指标的序列长度不一致，
两两对齐时错位（把 A 指标的第 3 个月对到 B 指标的第 5 个月）——这种错位不报错，
只会画出一条错的曲线。

周期字段为空的行**进不了任何统计**——区间过滤是在服务端做的，这些行压根不会返回。
所以每个板块会额外查一次该字段为空的条数，在板块开头如实标出
「另有 N 条记录因该时间字段为空，未纳入本报表任何统计」。
探测上限 500 条，超过会写成「至少 N 条」
（它们仍计入上方的总计）。

## `tz`：报表时区

省略即 `+08:00`（北京时间）。取值：`+08:00` / `-04:00` 这类偏移，或 `utc` / `local`。

**它决定周期的切分点，不只是显示格式。** 简道云存的是 UTC，界面按 +8 显示；
`this_week` 到底从哪一刻开始，取决于按哪个时区切。同一份数据用 `utc` 和 `+08:00`
各跑一遍，边界会差 8 小时——落在这 8 小时里的记录，一份报表算进来、另一份算出去。
两份都不报错，数字都看着合理。

**除非你的数据确实按别的时区录入，否则不要动它。** 报表页脚会回显实际用的时区，
那个标签由生成时间本身算出，不会和真正用的那个不一致。

## `period.range` 取值

| 取值 | 含义 |
|---|---|
| `last_7_days` / `last_14_days` / `last_30_days` | 含今天在内往前 N 天 |
| `this_week` / `last_week` | 周一起算 |
| `this_month` / `last_month` | 自然月 |
| `custom` | 需同时给 `start` 与 `end`（`YYYY-MM-DD`，end 当天算在内） |

**上期**恒为与本期等长、紧邻在前的区间，两者不重叠。

## `metrics[].agg` 取值

| agg | 需要 field | 说明 |
|---|---|---|
| `count` | 否 | 记录数 |
| `sum` / `avg` / `max` / `min` | 是 | 只统计能解析成数字的值，无法解析的跳过 |
| `distinct` | 是 | 去重计数，忽略空值 |
| `ratio` | 否 | **派生指标**：由其他指标相除得出，见下节 |

## `ratio`：派生指标（比率）

回款率、良率、达成率、库存周转率——**每个领域都要算比率**，所以放在引擎层。

```yaml
sections:
  - title: 销售订单
    entry: "..."
    period_field: 订单签订日期
    trend: month
    metrics:
      - {label: 订单金额, agg: sum, field: 销售订单金额(含税)/元}

  - title: 回款
    entry: "..."
    period_field: 回款日期
    trend: month
    metrics:
      - {label: 回款金额, agg: sum, field: 本次回款金额/元}
      # 分子在本板块，分母在「销售订单」板块 —— 跨板块引用
      - {label: 回款率, agg: ratio, numerator: 回款金额, denominator: 销售订单.订单金额}
```

- **引用写法**：`指标标签`（同板块）或 `板块标题.指标标签`（跨板块）
- **`as`**：`percent`（默认，输出 82.9%）或 `raw`（输出 0.829 / 3.0，适合周转率这类倍数）
- **趋势也会算**：两个板块的时间桶按同一区间预生成，所以即使用不同的
  `period_field` 也能对齐；粒度或区间不一致时**明确标注"未计算"而不是硬对**
- **分母为 0 或缺失 → 输出 `—`**，不是 0% 也不是 ∞。除零算出来的不是"很大"，是没有意义

其他领域的写法：

| 场景 | 配置 |
|---|---|
| 良率 | `{label: 良率, agg: ratio, numerator: 合格数, denominator: 送检数}` |
| 目标达成率 | `{label: 达成率, agg: ratio, numerator: 实际金额, denominator: 销售目标.目标金额}` |
| 库存周转率 | `{label: 周转率, agg: ratio, as: raw, numerator: 出库数量, denominator: 平均库存}` |
| 变更返工率 | `{label: 返工率, agg: ratio, numerator: 返工工时, denominator: 需求变更.总工时}` |

`field` 与 `dimensions` 都填**字段显示名**（不是 `_widget_` 标识）——
不确定就先用 `jdy-doc` 导一份数据字典。

## 常见问题

- **板块显示"本期无数据"**：多半是 `period.field` 选错了。示例数据常常是批量灌入的，
  所有记录的创建时间挤在同一时刻，这时用业务日期字段（如「跟进时间」「订单签订日期」）更有意义
- **趋势全挤在最后一个桶**：同上，说明周期轴用的是录入时间而非业务发生时间
- **百分比字段的值看着很小**：简道云的百分比类数字字段**存的是小数**（0.75 = 75%），
  做阈值分层时别拿 0~100 去比
- **数字明显偏小**：检查该字段是不是文本类型存的数字，或含单位/千分位——
  `sum` 会跳过解析不了的值而不是报错
- **维度里大量 `(未填)`**：该字段在多数记录里是空的，先用 `jdy-doc` 体检确认是不是孤儿字段
