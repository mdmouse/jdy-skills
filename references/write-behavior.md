# 写入行为与失败归因（batch_create 实测）

> **2026-08-27 对真实账号「测试/未命名表单」空表做的 14 次写入实验**，逐条回读核对实际入库值。
> 结论与官方文档有出入之处已标注。这是 `jdy-excel-bridge` 设计的事实基础。

## 一句话结论

**`batch_create` 是一个"静默失败"的接口。** 它几乎不做值校验：格式不对的字段被**默默存成 `null`**，
整行照样入库，响应照样返回 `{"status":"success","success_count":1}`。
只有**结构性**错误（超 100 条、空数组）才会返回 HTTP 400。

> ⚠️ **这条推翻了实施计划里 `import.py` 的设计。** 计划写的是"失败行按 error-codes.md 归因，
> 产出修复建议表"——但**API 根本不报失败行**。正确设计必须是：
> **preflight 预检 → 写入 → 回读比对 → 差异归因 → 修复重提**。
> 回读比对不是可选步骤，是唯一能发现脏数据的手段。

## 二、值必须用 `{"value": x}` 包裹 —— 裸值静默丢全行

| 写法 | 响应 | 实际入库 |
|---|---|---|
| `{"_widget_x": {"value": "E1-wrapped"}, ...}` | 200 success | ✅ 全部字段正确 |
| `{"_widget_x": "E1-bare", ...}` | **200 success** | ❌ **空行**：所有字段均为 `""` / `null` |

裸值格式**不报错**，返回 `success_ids` 也有值，但入库是一条彻头彻尾的空记录。
→ 客户端必须强制包裹格式，且**导入后回读**才能发现这类事故。

## 三、`transaction_id` 覆盖行为（与文档一致，但响应会骗人）

同一 `transaction_id` 提交两次：

| 次序 | 内容 | 响应 | 结果 |
|---|---|---|---|
| 第 1 次 | `E2-first`, 数字=10 | `success_count:1, success_ids:["6a90f0e4..."]` | 入库 |
| 第 2 次 | `E2-second`, 数字=20 | `success_count:1, **success_ids:[]**` | **覆盖第 1 次** |

回读确认：`E2-first` 已不存在，`E2-second` 存在且数字=20，总行数未增加。

→ 覆盖语义**成立**（文档所述 1 小时内幂等属实）。但**第二次的 `success_ids` 是空数组**，
拿不到数据 ID。客户端若靠 `success_ids` 长度判断成功与否，会误判成失败并重复重试。
**判定成功要看 `success_count`，取 ID 要看 `success_ids`，两者在覆盖场景下不一致。**

## 四、日期格式：只认三种，其余静默变 `null`

| 输入 | 入库结果 |
|---|---|
| `2026-08-27T00:00:00.000Z` | ✅ `2026-08-27T00:00:00.000Z` |
| `2026-08-27` | ✅ `2026-08-27T00:00:00.000Z` |
| `2026-08-27 10:30:00` | ✅ `2026-08-27T10:30:00.000Z` |
| `2026/08/27` | ❌ **null** |
| `27/08/2026` | ❌ **null** |
| `2026年8月27日` | ❌ **null** |
| `""` | ❌ **null** |

→ 「日期格式混杂」这个坑的真实形态**不是报错，是整列悄悄变空**。
Excel 里最常见的 `2026/08/27` 恰恰**不被接受** —— preflight 必须做日期归一化。

### ⚠️ 斜杠日期的日/月顺序：**不猜，报错**

`27/08/2026` 这类要归一化成 ISO 才写得进去，而归一化第一步就得决定
"前面那个数是日还是月"。归一化器里原来 `%d/%m/%Y` 排在 `%m/%d/%Y` 前面，
于是 `01/12/2025` **恒**被读成 12 月 1 日——谁在前是格式列表的先后顺序决定的，
等于抛硬币。而错了没有任何迹象：存进去是个合法日期，回读比对也通过。

现在的规则：

| 输入 | 处理 |
|---|---|
| `25/12/2025` | ✅ 25 只能是日 → 12 月 25 日 |
| `12/25/2025` | ✅ 25 只能是日 → 12 月 25 日 |
| `2025/12/25` | ✅ 四位年在前，从来不歧义 |
| `01/12/2025` | ❌ **报错**，要求把这一列改成 `YYYY-MM-DD` |
| `25/25/2025` | ❌ 报错（不是合法日期） |

歧义的那格会以 `bad_value` 进预检清单、指名道姓地说该怎么改，
而不是变成一个错日期躺在表里。

### ⚠️ 时区陷阱（含一个容易踩第二次的坑）

`2026-08-27 10:30:00` 存成了 `2026-08-27T10:30:00.000Z` —— **输入被当作 UTC 原样接收**。
对照本账号真实数据（员工档案「出生日期」= `1996-02-02T16:00:00.000Z`，即北京时间 02-03 00:00），
简道云存 UTC、按 +8 显示。
→ 用户 Excel 里写的北京时间若不带时区直接提交，**界面上会晚 8 小时**。

**第二个坑：不能用"机器本地时区"来补这个偏移。** 端到端实测中，脚本跑在 UTC-4 的机器上，
同一份 Excel 的 `2026/08/27` 在简道云界面显示成 `08-27 12:00`、`10:30` 显示成 `22:30`——
数学上换算无误，但源数据本是北京时间，结果整体偏了 12 小时，且界面上看不出异常。

→ 正确做法：**源时区必须显式指定**，默认 `+08:00`。内核 `DEFAULT_TZ` 即为此，
`parse_tz()` 支持 `+08:00` / `utc` / `-04:00` / `local`。校验基准：北京时间零点 = 前一日 `16:00Z`，
与简道云自身存储一致。

## 四之三、电话与地址（2026-08-28 实测）

| 字段 | 写法 | 结果 |
|---|---|---|
| `phone` | `{"phone": "13800138000"}` | ✅ 写入成功 |
| `phone` | `"13800138000"`（纯字符串） | ❌ 静默丢弃 |
| `phone` | `["138…"]` / `13800138000`（数字） | ❌ 静默丢弃 |
| `address` | `{province, city, district, detail}` | ✅ 写入成功 |
| `address` | `"江苏省无锡市锡山区…"`（拼接串） | ❌ 静默丢弃 |

两者都印证同一条规律：**读出来的显示值不是可写值**，与 `user` 字段同源。

## 四之四、系统生成的编号字段（2026-08-31 全账号扫描）

| 类型 | 中文名 | 处理 | 依据 |
|---|---|---|---|
| `sn` | 流水号 / 自动编号 | 拒绝写入 | 系统生成，且计数器可能与既有数据冲突 |
| `autonum` | —— | 拒绝写入（保险） | **这个类型名在 API 里根本没出现过**，见下 |

扫了本账号 6 个应用 **74 张表单**，出现过 **25 种**控件类型，`autonum` **一次都没有**；
而 `sn` 出现 14 次，字段名清一色是「订单编号」「客户编码」「报价单编号」这类——
**界面上的「自动编号」控件，通过 API 拿到的类型就是 `sn`。**

所以 `autonum` 更像是当初凭印象写进 jdy-devkit 形状表里的一个名字，
从来没有对应过真实的控件。它现在留在内核 `READ_ONLY_TYPES` 里纯属保险：
拦一个不存在的类型零成本，而万一某个版本/套餐真的返回它，
拦住也比放行安全——两种错法不对称：错拦一个能写的字段，
用户会在「未提交的字段」清单里看到类型和原因，一眼能推翻；
错放一个系统生成的字段，是静默写坏或静默丢弃，接口照样回报成功。

**这个结论的边界**：能证明的是"本账号 74 张表单里没有 autonum"，
不能证明"任何简道云账号都不会返回 autonum"。哪天真的见到一个，
按上面这条不对称原则，仍然应该先拦住再说。

## 四之五、写入形状实验（2026-08-31，逐类实测）

`UNVERIFIED_WRITE` 这份名单是全家的公共天花板：一个类型没实测过，
excel-bridge / sync / clean / restore 四条写路径就只能整列排除它。
用 `tests/real/write_probe.py` 逐类试过之后：

| 类型 | 能写的形状 | 写不进去的形状（**全部静默丢弃**） |
|---|---|---|
| `checkboxgroup` | `["销售"]` / `["销售","研发"]` 字符串列表 | `"销售"` 裸串、`"销售、研发"` 顿号串 |
| `combocheck` | 同上 | 同上 |
| `dept` | **裸 `dept_no` 整数**，如 `1` | 完整对象、`{"dept_no":1}`、`"mdmouse"` 部门名 |
| `company` | 纯字符串 | —— |
| `linkobject` | `{"link_id": "<data_id>"}` | 裸 data_id 串报 `3005`（不是丢弃，是报错） |

`dept` 与 `linkobject` 都是**写 ID、读回展开对象**，和 `user` 同一种读写不对称：

```
写 1                              → 读回 {"name":"mdmouse","dept_no":1,"type":0,…}
写 {"link_id":"6a8d7c40…"}        → 读回 {"link_form":"…","link_id":"6a8d7c40…","name":"示例：锡山简道云"}
```

`linkobject` 写进去的 `name` 会被接口**覆盖成目标记录的真名**——说明它确实解析了链接。

### ⚠️ 选项不校验，而元数据也不给选项列表

写一个**根本不存在的选项**，接口原样存下（checkboxgroup / combocheck 都是）：

| 写入 | 结果 |
|---|---|
| `["压根没有这个选项"]` | ✅ 原样存进去，界面上显示成一个不存在的选项 |

而 `widget/list` 对选择型控件只返回 `name/label/type/widgetName`，**没有选项列表**
——和"不返回 lookup 指向哪张表"是同一个缺口。所以校验不了，只能拿这一列的
历史数据当索引：preflight 会提醒"这个值在历史数据里没出现过"，但**不扣行**，
因为新增一个选项完全合法。这是启发式，不是权威。

### 清空字段只认空对象

| 写入 | 结果 |
|---|---|
| `{"value": {}}` | ✅ 字段被清空 |
| `{"value": null}` | ❌ `3005 The request contains invalid parameters` |
| `{"value": ""}` | ❌ `3005` |

（做同一行反复试写的实验时必须先清空，否则被静默丢弃的那次会留着上一次的值，
读回来看着像"存下但变形"。）

## 四之六、附件与子表单（2026-08-31 实测打通）

### 附件（`image` / `upload`）

三步，缺一不可（协议见官方《文件接口》 hc.jiandaoyun.com/open/13287）：

```
1) POST /v5/app/entry/file/get_upload_token {app_id, entry_id, transaction_id}
   → token_and_url_list[]      一次给 100 组 {url, token}，20 次/秒
2) POST {url}   multipart/form-data：token + file（**file 必须放最后**）
   → {"key": "<uuid>"}          上传主机是七牛 upload.qiniup.com
3) 把 key 写进控件，**且写入请求必须带上同一个 transaction_id**
```

第 3 步的值形状官方没写（参数说明页要登录），实测：

| 写入 | 结果 |
|---|---|
| `["<key>"]` 字符串列表 | ✅ 挂上去了 |
| `[{"key": "<key>"}]` | ❌ **静默丢弃** |

读回来展开成 `[{"name","size","mime","url"}]`，**文件名保留**：

```
写 ["0e541f1c-…"]  → 读回 [{"name":"att.txt","size":43,"mime":"text/plain",
                            "url":"https://files.jiandaoyun.com/0e541f1c-…?e=1789466399&token=…"}]
```

→ 又一个**写 ID、读回展开对象**的不对称（同 `user` / `dept` / `linkobject`）。

**读回来的值不能回灌**：url 带 `e=` 过期戳（实测约 15 天）。搬附件只能重新下载再上传。

⚠️ **凭证与事务都只有 1 小时有效期**，且 `transaction_id` 一旦用于分块写入会互相
覆盖（见本文第三节）——所以**带附件的批量写入一次最多 100 行**，
内核在超出时直接报错而不是默默拆块（默默拆会让后面几块的附件全部失效，
而接口照样回报成功）。

#### 更新（`data/update`）也能带附件（2026-08-31 实测）

先前只在**新增**路径上打通过，更新路径一直没验，于是导入工具把本地文件路径
当成 key 直接提交。实测两种写法：

| 更新时提交 | 接口 | 回读 |
|---|---|---|
| `["/Users/x/更新实验.txt"]`（本地路径当 key） | `success` | `[]` —— **空的** |
| 先上传拿 key，`update` 带**同一个** `transaction_id` | `success` | `[{"name":"更新实验.txt",…}]` ✅ |

→ **更新与新增走的是同一套三步流程**，`data/update` 的 body 同样接受
`transaction_id`。附件不是"新增专属"。

本地路径那一行是本项目的老朋友：接口回报成功、字段却是空的。
好在 `update()` 的逐字段回读把它标成了"提交了值但写入后为空"——
安全网接住了，但功能整个是坏的（`导出 → 改 → 导回` 这条官方推荐流程
永远搬不动附件）。

**取凭证是一次给 100 组**，所以一批文件应当**一次取够**再分发；
按单元格逐个取，50 行就是 50 次请求、白取 5000 组用 50 组，
而这个端点限流 20/s。

### 子表单（`subform`）

| 写入 | 结果 |
|---|---|
| `[{内层字段: {"value": v}}, …]` 双层包裹 | ✅ 写进去了 |
| `[{内层字段: v}]` 单层（**读回来就是这个形状**） | ❌ **静默丢弃** |
| `[]` | ✅ 清空 |

**update 是整表替换**：原来 2 行，写 1 行进去就只剩 1 行——不能只改其中一行。

读回来的每行还多一个 `_id`，且内层值**不包** `{"value": …}`——
所以子表单同样是"读回来的形状 ≠ 能写回去的形状"。

`encode_row` 的 subform 分支产出的正是能写的那个形状，所以**导入这条路是通的**；
同步要把源表内层字段按显示名映射到目标表内层字段，那是一个功能不是一行解锁。

## 四之七、搬运到另一张表（2026-09-01 实测 · W1）

前面几节验的是"能不能写进去"。**搬运**多一层：值是从另一张表**读回来的**，
而读回来的形状不是能写回去的形状。子表单与附件同步（jdy-sync）的四条前提，
在当天的 API 上逐条复核，原始输出见 `tests/real/subform_attach_probe.py`。

| 实验 | 结果 |
|---|---|
| a-1 create 写双层包裹 → 回读 | `[{"_id":"…","_widget_…649":"第一行","_widget_…650":1}, …]`——扁平、内层不包 `value`、每行多一个 `_id` |
| a-2 把**刚读回来的这份**原样写回去 | 接口 `success`，回读 `[]`——**整列被清空**（不是报错，是静默丢） |
| a-3 再用双层包裹写 2 行 | ✅ 回读 2 行；`update` 路径同样认双层包裹 |
| b 目标 2 行、写 1 行 | ✅ 回读只剩 1 行——**整表替换**在当前 API 上成立 |
| c `copy_attachments()` 首次真机调用 | ✅ 2 个附件搬到另一张表，回读拿得到文件名 |
| d 同一文件重传后的 `size` | ✅ 31748 → 31748，**逐字节稳定** |

→ 附件 diff 的比对键用 `(name, size)` 成立（sync D4）。但**有个前提**，见下。

### ⚠️ 搬运会改文件名——`copy_attachments` 首验就抓到（已修）

一格里两个**同名**附件（`timg (8).jpg` ×2），搬过去变成
`timg (8).jpg` + `timg (8)-2.jpg`：

```
源：      [{"name":"timg (8).jpg","size":31748}, {"name":"timg (8).jpg","size":31748}]
搬运后：  [{"name":"timg (8).jpg",…},            {"name":"timg (8)-2.jpg",…}]
```

成因是**两半不对称**：`download_file` 为了不覆盖同名文件，把第二个存成
`x-2.jpg`（那半是对的，附件重名太常见，覆盖等于悄悄丢文件）；
而 `upload_files` 默认拿**本地文件名**当上传文件名，当它没改过。

后果不是"名字难看"，是**幂等直接破了**：附件按文件名比对，源与目标永远对不上，
每次重跑都判"有变化"、重传一遍、再改一次名。

修法：`copy_attachments` 把**读回来的原始 name** 显式传给 `upload_files(names=…)`。
修后同一实验回读 `timg (8).jpg` ×2，name 与 size 都稳。

守它的测试：`tests/test_jdy_client.py TestCopyAttachmentsKeepsTheOriginalName`
（变异 70）。

|---|---|---|
| 数字字段传字符串数字 | `"123"` | ✅ `123`（自动转换） |
| 数字字段传非数字 | `"abc"` | ❌ **null**（静默丢弃） |

## 六、未知字段：静默忽略

混入不存在的 `_widget_0000000000000` → HTTP 200，该键被忽略，其余字段正常入库。
→ Excel 里多出来的列不会导致失败，但**也不会有任何提示**。preflight 必须显式列出"未映射的列"。

## 六之二、坑型字段写入实测（订单管理，2026-08-27）

**统一规则：每一层的每个字段值都必须 `{"value": x}` 包裹。** 少包一层就静默丢弃。

### `user` 成员字段 —— 读写格式不对称 ⚠️

| 写法 | 结果 |
|---|---|
| `{"value": "sys_xxxxxxxxxxxx"}`（username 字符串） | ✅ **唯一可行**，回读为完整成员对象 |
| `{"value": {"username": "...", "name": "hao"}}`（读回来的那种对象） | ❌ 静默丢弃 |
| `{"value": "hao"}`（显示名） | ❌ 静默丢弃 |

→ **读到的是对象，写回去必须是 username 字符串** —— 直接把导出结果回灌会全军覆没。
→ Excel 里用户填的是姓名，导入前**必须查通讯录解析成 username**；重名时无法自动判定，
   这就是「成员重名」坑的真实形态。

### `subform` 子表单 —— 内外两层都要包裹

```json
{"_widget_订单明细": {"value": [
    {"_widget_主键": {"value": "子表单行A"}, "_widget_单价": {"value": 11}},
    {"_widget_主键": {"value": "子表单行B"}, "_widget_单价": {"value": 22}}
]}}
```

✅ 两行均正确写入。内层若用裸值（`"_widget_单价": 11`），**整个子表单静默丢空**。

### `sn` 流水号 —— 系统生成，且会与既有数据冲突

自造 `"ZZZ-999"` 被忽略，系统生成 `00008`。
**但计数器从 `00001` 重新开始**——而表内既有示例数据已占用 `00007`，
新建行再次拿到 `00007` → **流水号重复**。计划里「流水号冲突」这个坑**实测成立**，
且成因是计数器与既有数据不同步，不是用户操作问题。

### `lookup` 关联数据 —— **可以写**，但没有引用完整性校验 ⚠️

把目标记录的 `data_id` 直接写进去，关系就建立了：

```json
{"_widget_关联字段": {"value": "deadbeefdeadbeefdead0005"}}
```

实测回读一致，关系确实生效。**但接口不校验引用是否存在**——写一个 24 个 0 的假 ID，
照样静默入库、照样回读"一致"。

> 这是本项目见过**最隐蔽**的一种脏数据：**连回读比对都发现不了**，
> 因为写进去什么就读回什么。必须自己查目标记录在不在。

麻烦在于 `widget/list` 对 `lookup` 只返回 `name`/`widgetName`/`label`/`type`，
**不说明它指向哪张表**。内核用反查解决：取该字段已有的几个引用 ID，
拿同应用各表单逐个 `data/get`，能查到的那张就是目标表
（`infer_lookup_target()` / `lookup_exists()`）。推断不出来时如实返回"无法校验"，
不谎称通过。

### `linkdata` 选择数据 —— 官方明示不支持 API 写入 🔴

穷举 **10 种**写法，**全部 HTTP 200 且全部静默失败**（回读恒为 `{}`）：

`{"id": x}` · 裸 id 字符串 · 不存在的 id · 显示名 · `[{"id": x}]` · `[x]` ·
`{"link_id": x}` · `{"id": x, "link_form": y}` · 顶层裸 `{"id": x}`（不含 value）· `{"value": {"id": x}}` 双层

目标记录经确认真实存在（取自客户信息表首条 `_id`）。

**单条 `create` 接口补测**：同样 HTTP 200、回读 `{}`，与 `batch_create` 行为一致。

→ **判定：`linkdata` 不可 API 写入，这是产品设计而非接口缺陷。**
   官方新建/修改数据文档原文即写明「选择数据……不支持添加和修改数据」，
   GUI Excel 导入的不可导入清单同样含选择数据。唯一写入方式是人在表单里手工点选。

→ **出路：换载体。** 简道云把可编程的表间关系押在了 `lookup`（关联数据）上，
   官方也提供「选择数据 → 关联数据」的迁移路径。所以正确的说法不是"关系搬不过去"，
   而是**"关系要换载体搬"**——目标表加一个 `lookup` 字段指向被引用表
   （需 GUI 操作，无表单结构创建 API），关系即可完整同步。
→ **对 `jdy-excel-bridge` 的影响是根本性的**：含 `linkdata` 的表**无法通过 API 完整导入**。
   技能必须在 preflight 阶段就检测出关联字段并明确告知用户"这些列导不进去"，
   而不是导完才发现整列是空的。`linkobject` / `lookup` 的写入行为待测。

## 七、真实错误码（会报错的只有结构性问题）

| HTTP | code | msg | 触发条件 | 修复动作 |
|---|---|---|---|---|
| 400 | `17024` | `The batch creation at one time exceeds the limit.` | `data_list` > 100 条 | 客户端分块 ≤100 |
| 400 | `3005` | `The request contains invalid parameter(s).` | `data_list` 为空数组 | 提交前过滤空批次 |
| 400 | `8303` | 超出请求频率限制 | 超过接口频率（batch_create 10/s） | 令牌桶 + 指数退避 |

> 错误码表远未完备——目前只采到写入路径这三个。权限类、字段校验类错误码待用最小权限 Key
> 做越权调用时补齐。

## 八、对 `jdy-excel-bridge` 的设计约束（直接结论）

1. **写入值一律 `{"value": x}` 包裹**，子表单内层同样要包，客户端不给裸值留出口
2. **导入必须三段式**：preflight 预检 → 分块写入 → **回读比对**；跳过回读＝交付脏数据
3. **preflight 承担全部校验**：日期归一化（含本地→UTC）、数字可解析性、
   成员名→username 解析（重名需用户裁决）、未映射列清单，
   并**显式标出 `linkdata` 列为"不可导入"**——这类列必须在导入前就告知用户
4. **成功判定看 `success_count`，ID 采集看 `success_ids`**，覆盖场景下二者不一致属正常
5. **分块严格 ≤100**，空批次提前过滤
6. 回读比对的差异报告，就是计划里说的"修复建议表"的真正来源
