### V1 · 豆包工作能否导入标准 SKILL.md　❌ 两轮均未通过——**文件复制这条路在该端走不通**

> 豆包工作是 2026-08-25 发布的**独立 Agent 产品，不是扣子**。

**2026-08-31 的判断是错的，2026-09-01 触发时被证伪。**
当时用 `install.py --discover` 扫出 `~/DoubaoWork/skills/`（客户端首次启动 22:13 自建），
把 11 个技能装了进去。**那个目录客户端根本不读。**

**触发实测（2026-09-01）**：在客户端里说「跑一下简道云探针」，Agent 的反应是——
去翻工作目录、查定时任务、检索企业内外部资料，最后反问「简道云探针具体指什么」，
并要用户提供脚本路径。

> 这个反应本身就是证据：**我们的 description 里白纸黑字写着「不要去翻工作区目录，
> 更不要回一句"目录是空的"」**。它做的恰恰是被明令禁止的那件事 ——
> 说明它压根没读到 SKILL.md，不是读了不听。

**查客户端代码定位到真正的落点**（只读 grep 它的前端资源）：

| 证据 | 结论 |
|---|---|
| 前端里 `localSkill` × 72、`SKILL.md` × 68、`skill_hub_empty_local_skills_cn` | 本地技能是**支持**的，有技能中心与"本地技能"分区 |
| 全量 grep：`~/DoubaoWork/skills` 这个路径**一次都没出现** | 我们装的地方它不认 |
| `~/Library/Application Support/DoubaoWork/` 下 `*skill*` 文件 **0 个** | 那不是技能注册表，是普通 Chromium 配置档 |
| `…/DoubaoWork/Default/.doubaowork/agent_mode/workspace/.skills/` 下**摆着它自带的近百个技能**，形态 `SKILL.md` + `references/` + `scripts/`，与我们一致 | **这才是真正的技能目录** |

**第二轮（2026-09-01 02:1x）：还是没通过，而且查出了更硬的原因。**

改到真实落点后再触发一次，Agent 仍然是先说「项目目录是空的」，再去搜文件系统，
最后**跑的是 `~/DoubaoWork/skills/hello-jdy/scripts/probe.py`**（那个错的旧目录），
还顺手读了仓库源码 `~/codes/py/jiandaoyun/skills/hello-jdy/`。
原始记录在该端自己的 trajectory 日志里：

```
python3 scripts/probe.py     # cwd = ~/DoubaoWork/skills/hello-jdy
读过：~/DoubaoWork/skills/hello-jdy/SKILL.md
     ~/codes/py/jiandaoyun/skills/hello-jdy/SKILL.md
```

**它是靠搜文件系统找到的，不是被技能系统触发的。**

**更关键的一条：我们装进 `.skills/` 的 11 个技能，被客户端删掉了。**
安装约 02:0x（当时从该路径跑探针成功），目录在 **02:14:24** 被改动，
再看已经只剩它自带的 101 个、`jdy` 一个不剩。机制在客户端偏好里写着：

| 偏好键 | 内容 |
|---|---|
| `saman/user_agent_workspace/remote_skill_install_info_v2` | 服务端下发的技能集，`progress: 100`、`status: READY` |
| `saman/user_agent_workspace/user_skill_sync_info_v2` | **用户技能，`skills: []` —— 空的** |

→ `.skills` 是**客户端按服务端清单同步管理**的目录，不在清单里的会被清掉。
用户技能走的是 `user_skill_sync_info_v2`，也就是**要经客户端登记到账号**，
不是往目录里放文件。

**所以两个文件落点都不行**：`~/DoubaoWork/skills` 客户端根本不读；
`.skills` 读，但下次同步就把外来的清掉。
`install.py` 仍指向 `.skills`（那确实是加载位置），但每次安装都会打印这条警告——
只写在文档里，下一个人照样会以为装完就完事。
顺带补了两处内核缺口——那个目录是 **`.skills`（点开头）**、且宿主名藏在祖先路径里：

- `install_root()` 原来只认 `skills`，点开头的认不出 → 该端永远报「未识别的宿主」；
- 根目录名是 `workspace`（太通用不能当签名），但路径里有 `DoubaoWork` 这一段，
  宿主匹配改成**先比根目录名、再往祖先找**。

改完从新落点跑探针：**宿主正确识别为「豆包工作」**。

| 导入方式 | 结果 | 证据 / 报错原文 |
|---|---|---|
| 放 `~/DoubaoWork/skills/` | ❌ **失败** | 客户端不从这里加载；Agent 只在**搜文件系统**时才撞见它 |
| 放 `…/.doubaowork/agent_mode/workspace/.skills/` | ❌ **失败** | 是加载位置，但**外来技能会被同步清掉**（实测 02:14:24 被清空） |
| **技能中心 → 导入本地技能**（界面） | ✅ **这条路通了**（2026-09-01 02:27/02:40） | 导入后文件落在 **`.user_skills/`**（与 `.skills/` 同级、互不相干），并登记进偏好 `user_skill_sync_info_v2`：`install_id` / `progress: 100` / `status: READY`。界面「我的技能 → 个人」区可见 |
| zip 包 | ⬜ | `dist/hello-jdy.zip` |
| `npx skills add` | ⬜ | |
| GitHub 链接 | ⬜ | 待仓库公开 |

- **通过标准**：导入后可被对话触发**且脚本执行**（探针 C1 出现在输出里）
- **降级方案**：用技能中心的"导入本地技能"界面手工导入；再不行用"对话创建技能"粘贴重建
**2026-09-01 02:2x 第三轮：分发这条路打通了，但还没到"通过"。**

用户在技能中心里做了「导入本地技能」，机制随即清楚：

- 导入的技能落在 **`.user_skills/`**——和服务端同步的 `.skills/` **是两个目录**，
  互不相干。之前一直盯着 `.skills/`，方向从一开始就偏了。
- 同时登记进偏好 `user_skill_sync_info_v2`：`install_id` / `progress: 100` / `status: READY`。
  **这份登记是"留得住"的那一半**，光有文件不够。

**但还差两件事，都会让下一次触发得出错误结论**：

1. **只导进去 2 个**（`hello-jdy`、`jdy-clean`），登记表与 `.user_skills/` 目录两边都是 2 个。
   其余 9 个还只是"本地扫到"，没进账号。
2. **导进去的 `hello-jdy` 是过期版本**：`.user_skills/hello-jdy/scripts/probe.py` 是 **v0.1.0**，
   没有 C10、也没有那个未识别宿主崩溃的修复。来源是 `dist/hello-jdy.zip`——**08-27 打的**，
   而 `dist/` 是 gitignore 的产物目录，没人盯着它，构建校验也只管 `skills/` 里的 vendor 副本。
   已重打全部 11 个 zip（探针 v0.3.0），并在 `install.py --list` 加了过期警告：
   dist 里的 zip 比 skills/ 旧就报出来，免得下一个人又导进一份几个版本前的东西。

- **结论**：**不通过。复制文件这条路在豆包工作上走不通**——不是路径没找对，
  是该端的技能目录由服务端清单同步管理，外来技能留不住。
  下一步只剩客户端「技能中心 → 导入本地技能」，把技能登记到账号。
  **两条判定口径的教训**：① 目录存在 ≠ 客户端从那里加载；
  ② **装进去了 ≠ 留得住**——第二轮如果只看"探针跑出来了"就判通过，
  会把一个靠文件系统搜索撞见的结果当成技能被触发。

不构成对事实 4 的否证。客户端刷新市场后复核归实装那一步做，不在本节下结论。

#### 事实 6 已实测（2026-09-01）：个人视角真的看不到

在千问办公里**用官方 AI 连接**问「简道云示例应用的员工档案有多少行？」，调用序列：

```
mcp__jiandaoyun__member_app_entry_list   app_id=deadbeefdeadbeefdead0001     → 定位表单
mcp__jiandaoyun__get_tool_help           tool_name=member_data_list
mcp__jiandaoyun__member_data_list        app_id=…, entry_id=5d5e533a…, limit=100
    → 报错 4010：Do not have permission to process data.      ← **个人视角被拒**
mcp__jiandaoyun__get_tool_help           tool_name=member_managed_data_list
mcp__jiandaoyun__member_managed_data_list 同参数                → 34 行
```

**34 行与本地 `jdy-query` 当场取的基准逐字一致。**
→ **T2 的「查数与本地基准逐字一致」这一步完成**，且走的确实是官方连接器。

要点两条，填表时别丢：

- **`member_data_list`（个人视角）在这个账号上直接被 4010 拒了**，
  能取到数的是 `member_managed_data_list`（管理范围）。
  「数据范围与授权者一致」不是一句抽象描述——**它会让最常用的那个读工具直接不可用**。
- 官方连接器给出的数与技能轨一致，说明**读侧两条轨在这张表上等价**；
  差异不在数字，在**能不能读到**。

#### 事实 6：两条轨的权限模型不是一回事

| | AI 连接（MCP 轨） | 技能轨 |
|---|---|---|
| 凭证 | 成员**个人**授权链接 | 企业级 **API Key** |
| 数据范围 | **与授权成员本人的权限一致** | 与 Key 勾选的应用／接口一致 |
| 写入能力 | 单条新增，且需管理员审核 | 全量写接口 |
| 护栏 | 平台侧（成员权限） | 本仓库侧（allowlist／dry-run／备份／回读） |

→ **核对基准时必须用同一成员视角**。用管理员 Key 查出 200 行、用普通成员的 AI 连接查出 80 行，
行数对不上不是 bug，是两套权限模型——这一条不写清楚，后面每次比对都会误判。

#### 结论

- **通过标准**：三端至少两端可用官方 AI 连接查数。
- **MCP 轨承接范围**：由「查数问答」扩为「**查数 ＋ 结构发现**」——
  新增的 `member_app_entry_widget_list` 让它能列字段，这是原来没有的一类能力。
- **技能轨独占（AI 连接 12 项工具里一项都没有）**：批量写入、更新、删除、
  审批动作、催办、通讯录读写、附件进出、跨应用同步。
  写侧唯一的 `member_data_create` 是**单条新增**，且要管理员审核。
- **状态**：服务端就绪且能力面已扩；三端**一端都还没实装**，本项仍未达 2/3 通过线。

> **优先级判断（据本次更新重估）**：有效期减分项消失、工具从 4 项扩到 12 项，
> MCP 轨的**通道价值上升**；但护栏与引擎价值不受影响——12 项里没有一项能替代
> 预检／备份／回读／规模闸门。故 V5 仍不构成阻塞项，
> 但「官方连接器实装」已从可选变成**上架前置**（要证实事实 4，也要取批量导入的行为基线）。

## 阶段 4：jdy-flow-ops 流程接口实测（2026-08-28）

**接口版本是混的**：数据 v5、流程读 v6、流程写 v1/v2。内核已改为支持带版本前缀的路径。

| 用途 | 路径 | 频率 |
|---|---|---|
| 查询我的待办 | `/v6/workflow/task/list` | 20/s |
| 查询流程实例 | `/v6/workflow/instance/get` | 30/s |
| 同意 / 否决 / 转交 | `/v1/workflow/task/{approve,reject,transfer}` | 20/s |
| 回退 | `/v2/workflow/task/rollback` | 20/s |

**写操作逐个实测**（销售CRM/缺货申请 的「审批节点」）：

| 操作 | 结果 | 数据层核对 |
|---|---|---|
| approve | ✅ | `status=1`／`result=1`，`finish_action=forward` |
| reject | ✅（未带 comment 也通过） | `status=1`／`result=0`，`finish_action=reject` |
| rollback | ❌ `50040` 节点未开启回退 | 实例未受影响 |
| transfer | ❌ `5049` 节点未开启转交 | 实例未受影响 |

**最重要的一条：流程写接口失败时返回 HTTP 200 + `status:"failure"`。**
`50040` 与 `5049` 都是这样返回的——不做检查就会把失败报成"成功 1 条"，
而流程实例纹丝未动。内核已在 `post()` 里识别并抛错，这条修复在本次实测中被验证。

### WorkBuddy 端到端验证（2026-08-28）

在 WorkBuddy 里让它「把那几条流程验证的申请退回去」，三项观察点全过：

| 观察点 | 结果 |
|---|---|
| 先 dry-run 再执行 | ✅ 主动跑 dry-run 列出会动哪些 |
| 撞上非交互拦截 | ✅ 停下来向用户确认，并特意点出「退回的是**别人的**申请」 |
| **如实转述 HTTP200 包着的失败** | ✅ 「3 条全部失败，报 50040……这是流程设计未开启回退权限的**配置问题，不是系统故障**」 |

数据层核对：3 个实例仍「进行中」、待办仍 3 条、审计日志三条失败记录带原因——与它的转述完全一致。

**第三项是这次最关键的验证**：`50040` 是 HTTP 200 + `status:failure` 返回的，
没有内核那道检查就会被报成"已退回 3 条"，而流程纹丝未动。

**同时暴露一个文档缺口**（已补）：它收到 `50040` 后去翻 `act.py` 找更合适的 `back_type`，
属白费功夫——该码意味着节点根本没开回退，调参数无用。SKILL.md 已明确写"收到这两个码不要再试参数"。

**另一个已补的缺口**：`task/list` 只返回元数据、零业务字段，同表单的多条待办在列表里
完全一样；而人指代审批永远靠内容。现已默认拉取业务内容并支持 `--contains` 按内容筛选——
补上之后它立刻能精确列出三条的申请标题与物料编码。

其他实测事实：`username` 必须是成员编号（传显示名报 `1010`）；
流程实例**提交时才创建**，配置流程之前的旧数据行查实例报 `50016`，这不是故障；
API 写入需显式 `is_start_workflow: true` 才触发流程。

## 三端适配的做法：探测，不按平台名分支（2026-08-31）

上面那条"取三端交集作为基线"在实施时改了做法。原因很直接：
**交集要等三端都测完才知道，而每加一个端就要重算一次。**
更麻烦的是"沙箱允许写哪儿"这件事——WorkBuddy 的白名单能从它的 `settings.json`
翻出来，另外两端翻不到，而且随版本会变。

所以改成运行时探测，落在 `_shared/platform_env.py`：

| 做什么 | 怎么做 | 为什么不写死 |
|---|---|---|
| 认宿主 | 从**技能自己被装在哪**反推（`<宿主目录>/skills/<技能名>/…`） | 这个形状对**没见过的端**同样成立；认不出就报出安装路径，那正是要回填的事实 |
| 找可写目录 | 按 `$JDY_HOME` → `~/.jdy` → 宿主配置目录 → 会话工作目录 → 临时目录逐个**实写**探测 | 各端白名单不同且不可知；`os.access` 看的是权限位，沙箱的拒绝在系统调用层，它会说"能写"然后写崩 |
| 读密钥 | **与状态目录分开解析** | 状态是我们写的，找个能写的地方就行；配置是用户写的，只能到他放的地方找。绑在一起就会"状态一降级、密钥跟着丢" |

**宿主标识只进报告，绝不进 if 分支**——有一条测试专门守着这一点
（`test_host_id_never_reaches_behavior`）。一旦按平台名分支，
没见过的端就又回到"不支持"，而本模块存在的意义就是不这么干。

### 顺带修掉的一个真问题

`~/.jdy` 不可写时，旧代码是**就地放弃**：字段缓存退成内存（可接受），
但 `jdy-flow-ops` 的**审计日志直接丢**（不可接受）。
于是在 WorkBuddy 上每一次批量审批都没有留痕——而同一时刻会话工作目录明明可写。

审批是有责任归属的动作。"沙箱不让写"不该等于"不留痕"，只该等于"换个地方留"。
现在它会一路找到能写的地方，并在屏幕上打印实际落点；
真的一个都找不到时才说「操作已执行但没有留痕」。

同一处改动也覆盖 `jdy-watch` 的去重状态：落在会话工作目录或临时目录时**下一轮找不回来**
（等于每轮重报），这一条会明说，而不是让用户以为哨兵记住了。
